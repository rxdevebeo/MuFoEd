## Этап 1. Стоимость транзакции (2–3 дня)

### 1.1. Что сейчас стоит каждая транзакция

`Editor::transact` при **любой** правке, даже вставке одного символа:

| Шаг | Стоимость |
|---|---|
| `self.document.clone()` → кандидат | O(документ) |
| `apply` → `all_ids(document)` на **каждую** команду пакета | O(документ) × команд |
| `split_shared_notes` | обход всех историй |
| `validate(&candidate)` | тело + `nesting::check_document` + стили/нумерация/секции + все истории |
| `same_content` | сравнение всех историй |
| `snapshot_size` ×2 | **Debug-сериализация** обоих документов целиком |
| `Snapshot { before: clone, after: clone }` | ещё 2 × O(документ) памяти |

Итого ~4 полных клона, 2 Debug-прохода и 3+N полных обходов на нажатие клавиши, а лимит
истории 64 MiB по Debug-оценке на документе в 1–2 МБ даёт всего десятки шагов undo.

### 1.2. Целевая модель: патчи по диапазонам блоков верхнего уровня

Каждая команда трогает ровно одну историю (`Story`) и в ней — один блок верхнего уровня
(`Address.block` для тела, или внешний контейнер `Address.containers[0]`); Join/Insert/Delete
дополнительно сдвигают соседей. Отсюда единица изменения:

```rust
struct Patch {
    story: Story,
    /// Диапазон блоков верхнего уровня истории *до* правки.
    before_range: Range<usize>,
    before: Vec<Block>,
    /// То, что встаёт на место `before_range`.
    after: Vec<Block>,
}
struct Transaction { patches: Vec<Patch>, notes: Option<NotesPatch>, bytes: usize }
```

Алгоритм `transact`:

1. Для каждой команды определить `(story, top_index)`; при первом касании скопировать
   **только этот блок** в рабочий набор (`BTreeMap<(Story, usize), Vec<Block>>`), команды
   применять к рабочему набору. Структурные команды (Insert/Delete/Join/Split на верхнем
   уровне) расширяют диапазон.
2. Сноски: `split_shared_notes` запускать только если затронутые блоки содержат ссылки на
   сноски (флаг, собранный при копировании); иначе пропуск.
3. Проверка — инкрементальная (§1.4) по рабочему набору.
4. Если рабочий набор равен оригиналу — no-op (сравнение только затронутых блоков).
5. Коммит: `splice` каждого диапазона в живой документ; в историю — `Transaction`.
6. Undo/redo — обратный/прямой `splice` по сохранённым патчам (в обратном порядке для undo).

Выбор против альтернатив:

- **`Arc<Block>` / персистентные структуры в модели** — затрагивают `wml::model` и все
  крейты-потребители (render, write, convert); отложено, пока замеры §0.1 не покажут, что
  патчей мало.
- **Обратные операции (command inverse)** — у 19 вариантов `Edit` свои инверсии, и каждая —
  место для ошибки; патч по блокам инвертируется тривиально.

### 1.3. Размер истории без Debug

`fn approx_size(&Block) -> usize`: обход блока с суммой длин текста + константа на узел
(абзац, ран, ячейка, рисунок). Это на порядок дешевле Debug-прохода (проверить замером
§0.1) и считается только по блокам патча. `with_history_byte_limit` сохраняет смысл (оценка, не точный RAM-бюджет) —
документировать новую формулу.

### 1.4. Инкрементальная проверка

| Инвариант | Сейчас | Цель |
|---|---|---|
| уникальность `w14:paraId` | `all_ids` на каждую команду + `validate_blocks` | `Editor.ids: HashSet<String>`, обновляется по патчу (минус id из `before`, плюс из `after`) |
| стили абзацев/ранов существуют | обход всего | только блоки рабочего набора |
| `nesting::check_*` | весь документ, **с лимитами по умолчанию** | рабочий набор, с лимитами документа (см. §3.4) |
| секции: число `sectPr` = число секций − 1 | весь документ | пересчёт только если патч содержит/удаляет `sectPr` |
| стили / нумерация / ссылки колонтитулов (`validate_global_references`) | каждая транзакция | стили и нумерацию команды не меняют — один раз в `Editor::new`; ссылки колонтитулов — только если патч затрагивает `sectPr` (`ParagraphProperties`, Split/Join/Delete абзаца с границей секции) |
| `Editor::validate()` (публичный) | полный | остаётся полным — для явного вызова и для тестов |

### 1.5. Приёмка этапа 1

- `tests/property.rs` зелёный без изменений + новый property-тест **эквивалентности**: та же
  случайная последовательность через старую реализацию (сохранить как `#[cfg(test)]
  mod reference` на один релиз) и через новую даёт байт-в-байт тот же `Document` и тот же
  результат принят/отвергнут.
- Бенчмарк 10 000 абзацев, «набор текста»: время транзакции не зависит от размера документа
  (в пределах ×2 между 1 000 и 10 000 абзацами); память истории на шаг ≈ размер одного абзаца.
- 1 000 шагов undo набора текста в документе 10 МБ укладываются в 64 MiB.

## Этап 2. `ChangeSet` для инкрементальной перевёрстки (1 день, после этапа 1)

### 2.1. Проблема

`Editor::changes(true)` возвращает `paragraphs = 0..body.len()` — «изменилось всё тело»;
колонтитулы, сноски, ячейки и надписи не адресуются вовсе. Потребитель не может
перерисовать один абзац. `Operations` (`replace_all`, `move_block`, `move_row`) отдают
тот же `ChangeSet`.

### 2.2. Новая форма (аддитивно)

```rust
pub struct ChangeSet {
    pub revision: u64,
    /// Устарело: индексы блоков тела, как раньше (для EditSession — точные).
    pub paragraphs: Vec<usize>,
    /// Что изменилось, по историям.
    pub blocks: Vec<BlockChange>,
    pub invalidate_layout: bool,
    pub invalidate_support: bool,
}
pub struct BlockChange {
    pub story: Story,
    /// Диапазон блоков верхнего уровня в документе *после* правки.
    pub range: Range<usize>,
    /// Сколько блоков стояло на этом месте до правки (≠ range.len() при вставке/удалении).
    pub replaced: usize,
}
```

`ChangeSet` строится прямо из патчей этапа 1; для undo — из обратных патчей. `paragraphs`
заполняется из `blocks` для `Story::Body` и помечается `#[deprecated]` в следующем минорном
релизе. Добавить `#[non_exhaustive]` на `ChangeSet`, чтобы следующие поля не ломали API.

### 2.3. Потребители

- **`VisualMap` / `visual_map`** сейчас делает **два полных `place_pages`** на каждый вызов
  (исходный и «окрашенный» для атрибуции). `ChangeSet.blocks` — вход для кэша раскладки по
  блокам верхнего уровня; сам кэш — отдельная задача в `render-svg` (раскладка зависит от
  секции и от плавающих объектов предыдущих блоков, поэтому инвалидировать надо «от первого
  изменённого блока до конца секции»). В рамках этапа 2 — только документировать контракт.
- **Фасад `DocumentEditor`** — пробросить новые поля.

### 2.4. Приёмка этапа 2

- property-тест: для каждой принятой транзакции `ChangeSet.blocks` покрывает *ровно* те
  блоки верхнего уровня, которые отличаются (сравнение снимков до/после по историям).
- undo возвращает `ChangeSet`, обратный исходному.

## Этап 3. Остальное (по убыванию пользы)

### 3.1. Never-crash для крейта (0,5 дня)

`clippy::indexing_slicing` в `strict-ooxml-edit` (сейчас `blocks[at.block] = …`,
`blocks.remove(at.block + 1)` и т.п. защищены проверками выше, но линт это не видит),
по образцу `pdf`/`convert`/`write`. Property-тест уже ловит панику на случайных адресах.

### 3.2. Лимиты документа вместо лимитов по умолчанию

`validate` вызывает `nesting::check_document(document, &ResourceLimits::default())`: документ,
открытый с более мягкими лимитами, может стать нередактируемым, с более жёсткими — получить
правку, которую reader бы не принял. `EditLimits { resource: ResourceLimits, .. }`, фасад
передаёт лимиты из `OpenOptions`.

### 3.3. `FormatPatch` шире (1 день)

Сейчас: bold, italic, underline, character style. Добавить с той же семантикой
`Option<Option<T>>` («не трогать» / «снять прямое значение» / «задать»):
размер (`w:sz`/`w:szCs`), цвет, выделение (`w:highlight`), шрифты (`w:rFonts` ascii/hAnsi/
eastAsia/cs), зачёркивание (`w:strike`/`w:dstrike`), верхний/нижний индекс (`w:vertAlign`),
`w:caps`/`w:smallCaps`. Тесты: round-trip через writer и reader, property — формат не меняет
текст.

### 3.4. Границы графем (0,5 дня)

`Edit::Text`, `Edit::Split`, `Edit::Format` принимают смещения в скалярах Unicode и могут
разрезать эмодзи с ZWJ, флаг или букву с комбинируемым знаком. Проверку границ сейчас делает
только `visual`. Предложение: `EditLimits::grapheme_boundaries: bool` (по умолчанию `false` в
этом релизе, `true` в следующем), при `true` — `EditError::InvalidRange` для конца диапазона
внутри кластера. `unicode-segmentation` становится обязательной зависимостью (она уже
в дереве через `visual` и `render-svg`).

### 3.5. `EditError` с данными

После `EditFailure` осталось: `UnsupportedContent` не говорит, *что* за содержимое
(поле, отслеживаемая правка, SDT); `UnknownStyle` — какой стиль. Варианты с данными ломают
`PartialEq`-сравнения в тестах — делать вместе с переходом тестов на `matches!`.

### 3.6. Отслеживаемые изменения (отдельный этап, 3–5 дней)

Сейчас абзац с `w:ins`/`w:del` отклоняется (`UnsupportedContent`). По шагам:

1. **Принять/отклонить:** `Edit::AcceptRevision { at, id }` / `RejectRevision` и «всё в
   истории» — writer уже умеет обёртки ревизий, reader их хранит в `Run.revision`.
2. **Правка поверх ревизий без трекинга:** `plain_runs` научить пропускать/сохранять раны с
   `revision`, если диапазон их не задевает.
3. **Авторская правка с трекингом:** `Edit::Text` с `track: Some(Author)` порождает
   `w:ins`/`w:del` с датой; Split/Join — `w:pPr/w:rPr/w:ins` для знака абзаца.

Каждый шаг — свой property-тест (accept-all ∘ правка = правка без трекинга).

### 3.7. Мелочи

- `Editor::find` — линейный поиск по всем адресам истории; с этапом 1 держать индекс
  `ParaId → Address` рядом с множеством id.
- `trim_history` удаляет из `redo` через `remove(0)` (O(n)) — `VecDeque`.
- **Дробление ранов.** Каждая вставка через `replace_text` режет ран на «до / вставка / после»
  и не склеивает соседние раны с равными свойствами: 50 нажатий в одном абзаце дают десятки
  ранов (замер теста истории: 2,5 МБ истории на 50 шагов в документе 1,8 МБ). Склеивать
  соседние `Run` с равными `props`/`revision` после `replace_text`/`format_text` — как Word. **Сделано
  для `replace_text`** (склейка на швах правки); `format_text` пока не склеивает.
- README крейта: раздел «стоимость операций» после этапа 1 с цифрами из §0.1.
