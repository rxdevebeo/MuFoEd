# ADR-0011: One MSRV for the workspace — 1.92

- **Status:** Accepted
- **Date:** 2026-09-30
- **Deciders:** Strict OOXML maintainers
- **Related:** `STAGE-8-TASK.md` §2 (dependency table), §2.1 (amended),
  `SESSION-HANDOFF-STAGE8.md` §2; `STAGE-8-OPEN.md` `O-3`, `O-11`, `R-7`, `O-2`

## Context

`STAGE-8-TASK.md` §2.1 planned a floor of **1.85** — the highest MSRV among the
stage's dependencies (`subsetter`, `ureq`) — and said the page rasterizer
(`hayro`, 1.92) would sit *outside* the MSRV gate because it is not in the
default build. That plan has two problems:

1. **The gates are not the default build.** CI runs
   `cargo clippy/test --workspace --all-targets --all-features`, so `--all-features`
   is the build the project actually gates on. A dependency that only needs 1.92
   under a feature still makes the gated build need 1.92.
2. **The rasterizer is not an option.** It is the planned path for the pixel-level
   PDF gate (`O-2`, the only project-level red that is not a bug in someone else's
   rework) and for recognising pages without a text layer (`O-11` / `R-7`). Those
   are acceptance criteria, not conveniences.

The declared number was also fiction in the other direction: the manifest said
`1.75` while the dependency graph needed 1.88 (`lopdf` 0.45). A floor nobody
verifies is not a floor.

## Decision

`rust-version = "1.92"` for the whole workspace, and a CI job that makes the
number true.

- `Cargo.toml` `[workspace.package] rust-version = "1.92"`.
- New job `msrv (1.92)` in `.github/workflows/ci.yml`:
  `cargo check --workspace --all-features --locked` on `dtolnay/rust-toolchain@1.92.0`.
  `--all-features` so the floor covers the gated build; `--locked` so the answer
  is about this tree rather than about what the resolver would pick today.
- No `rust-toolchain.toml`. CI deliberately tracks `@stable`/`@nightly` channels
  (ADR-0006's rasterizer pin, the coverage job's `llvm-tools`), and a pinned
  channel file would quietly override every contributor's toolchain to make one
  number convenient.

## Amendment (2026-10-03, AUD-88)

Upstream `hayro` 0.7.x / `hayro-interpret` 0.7.0 / `hayro-syntax` 0.7.2 does not
bound recursive paint (tiling patterns, Type 3), absurd image dimensions, or
huge CID `/W` ranges. The process then stack-overflows or hangs after our own
limits have already passed. The workspace therefore vendors those three crates
under `vendor/` with the PrintCraft patches (`MAX_PAINT_NESTING`,
`MAX_IMAGE_PIXELS`, `MAX_CID`, page-tree cycle guard), wired by
`[patch.crates-io]` in the root `Cargo.toml`. Licence remains Apache-2.0 OR MIT;
accounting is in `vendor/README.md` and `docs/ATTRIBUTION-vendor-hayro.md`. The
vendored copies are removed once upstream ships equivalent fixes. Hostile
raster inputs are gated by `strict-ooxml-pdf/tests/hostile.rs` `mod raster`
under `--features raster` / `--all-features`.

## Consequences

- **Cargo enforces the floor**, which is the entire point: a 1.91 toolchain now
  refuses to build the workspace with a clear message instead of failing later in
  a dependency. On the machine this was decided on, the default `stable` is
  1.91.1 and the installed 1.98.0 is the toolchain to work with
  (`cargo +1.98.0 …`, or `rustup update stable` to move the default).
- Users on 1.85–1.91 cannot build. The set is small and shrinking, and they were
  already building something the manifest did not promise.
- The floor can go back down if the rasterizer is replaced by something that does
  not need 1.92. It is a decision about a dependency, not a position on Rust.
- The MSRV job is a *check*, not a declaration: the ADR template's «validation»
  section for this decision is a CI job, and a number that only lives in a
  manifest would be exactly the kind of unverified claim this project keeps
  catching in its own renderers.

## Alternatives considered

1. **Keep 1.85, exclude the rasterizer from the gate** (the order's original
   plan). Rejected: two floors, one of which is not the one the gates use. In
   practice the first person to run `--all-features` on 1.88 would have found out
   the hard way.
2. **Keep the declared 1.75 and let each dependency speak for itself.** Rejected:
   the manifest is the only place a user can learn the answer, and it was wrong.
3. **Raise to the latest stable (1.98) rather than the minimum that works.**
   Rejected: an MSRV is a floor for users, not a mirror of the maintainers'
   toolchain. It rises only when a dependency forces it.
4. **Add `rust-toolchain.toml` pinning 1.92.** Rejected: it overrides contributors
   and CI channels to serve a number cargo already enforces from the manifest.

## Validation

- `cargo check --workspace --all-features --locked` on 1.92.0 — the CI job.
- `cargo +1.98.0 check --workspace --all-features` locally: green.
- A 1.91 toolchain refuses with «requires rustc 1.92», which is the floor working
  rather than a claim about it.
