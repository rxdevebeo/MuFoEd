**Шифр:** ZAKAZ-CORE-1 (REWORK-CORE-1)  
**Крейт:** `strict-ooxml-core`  
**Основание:** проверка новых файлов `strict-ooxml-core/tests/samples/` (в рамках приёмки Этапа 4), обнаружено ложное срабатывание лимита  
**Обнаружил:** приёмка (независимая проверка корпуса)  
**Дата:** 2026-09-28  
**Приоритет:** высокий (файл не открывается вовсе; влияет на корпуса и реальные документы)

> Только требования и критерии приёмки. Код не приводится.

## 1. Проблема C-1 (основная). Ложное срабатывание `max_compression_ratio`

**Факт.** `strict-ooxml-core/tests/samples/sample-docx-200kb.docx` (201 КБ)
отклоняется с ошибкой:
```
error: resource limit exceeded (compression_ratio): limit = 200, actual = 44153871
```

**Разбор (доказано):**
- файл — легитимный стресс-документ: **88 481** повторяющихся абзацев
  (`<w:p>` = `<w:r>` = `<w:t>` = 88 481; текст «Lorem ipsum…»);
- `word/document.xml`: 193 805 Б сжатый → **44 153 871 Б** распакованный;
- **отношение = 227.8** > дефолта `max_compression_ratio = 200`;
- абсолютные ограничители (`max_single_uncompressed` = 128 МиБ,
  `max_total_uncompressed` = 512 МиБ) 44 МиБ **пропускают** — срабатывает только
  отношение.

**Почему это дефект.** Монотонный, но валидный XML deflate сжимает лучше 200:1
(теоретический максимум ≈ 1032:1); дефолт 200 даёт **ложные отказы** на реальных
документах, при том что память уже ограничена абсолютными лимитами. Файл
полностью нечитаем (`inspect`/`check`/`report`/`render` падают).

**Требование.**
1. Устранить ложное срабатывание: поднять дефолт `max_compression_ratio` до
   безопасного значения (рекомендуется **1000**, порядок максимального отношения
   deflate) **или** сделать проверку отношения **вторичной** к абсолютным
   лимитам (отношение — эвристика против бомб, абсолютные размеры — основной
   барьер).
2. Сохранить защиту от zip-bomb: истинная бомба (малое сжатое → огромное
   распакованное) по-прежнему должна отклоняться по `max_single_uncompressed`/
   `max_total_uncompressed` и/или новому порогу отношения.
3. Значения лимитов остаются переопределяемыми через `OpenOptions`
   (регрессия для пользователей, которым нужен строгий порог).
4. Обновить документацию (`limits.rs`, ТЗ §12.1) и обоснование значения.

**Критерии приёмки C-1.**
1. `Package::open_path("sample-docx-200kb.docx", &OpenOptions::default())` →
   **Ok** при дефолтных лимитах.
2. Искусственная бомба (например, запись с отношением ≥ 1000:1 и распакованным
   размером сверх `max_single_uncompressed`) → **LimitExceeded** (защита цела).
3. Тест-регрессия: `sample-docx-200kb.docx` (или аналогичная фикстура) при
   дефолте открывается; при явно заданном `max_compression_ratio: 200` —
   отклоняется.
4. Обновлён `limits.rs` (дефолт + doc) и ТЗ §12.1; `xfail`/`xfail`-обходы
   отсутствуют.

> **Уточнение исполнителя (C-1, критерий 1).** `sample-docx-200kb.docx` —
> **Transitional**, поэтому при `OpenOptions::default()` (StrictOnly) он законно
> возвращает `TransitionalNotSupported`, а не `Ok`. Дефект был именно в лимите;
> проверка выполняется через `ConformancePolicy::Permissive`: файл должен
> открываться без `LimitExceeded`. Детали — `docs/core-limits-audit.md`.

## 2. Проблема C-2 (мелкая). Неверное поле `actual` в ошибке отношения

**Факт.** `StrictError::LimitExceeded { kind: CompressionRatio, limit: 200,
actual: 44153871 }` — `actual` равен **распакованному размеру в байтах**, а не
отношению (227.8). Диагностика вводит в заблуждение (сравнивает байты с
безразмерным порогом).

**Требование.** В `LimitExceeded` для `CompressionRatio` сообщать **отношение**
(в сопоставимой с `limit` единице), при необходимости — с размером в тексте
сообщения, но не в `actual`.

**Критерий приёмки C-2.** Сообщение показывает отношение (≈227), а не байты;
обновлён тест на формат/значение `actual`.
