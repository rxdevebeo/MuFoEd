## 3. P0 — R1. Устранение O(n²) в XML-парсере

### 3.1. Проблема
`strict-ooxml-core/src/xml/mod.rs:359` — `location()` вычисляет строку/колонку
сканированием `self.data[..offset]` **от начала буфера при каждом вызове**.
Вызывается безусловно на каждом элементе: `open_element` (`:229`),
`close_element` (`:271`). Итог — O(n²).

### 3.2. Замер (release, синтетический `<w:p><w:r><w:t>`)
```
n= 2000  bytes=   68 KB  events=  14 002  time=    157 ms
n= 4000  bytes=  136 KB  events=  28 002  time=    624 ms
n= 8000  bytes=  272 KB  events=  56 002  time=  2 651 ms
n=16000  bytes=  544 KB  events= 112 002  time= 16 623 ms
n=32000  bytes= 1.09 MB  events= 224 002  time= 67 896 ms
```
Нарушает НФТ ТЗ §14 (разбор 100-страничного документа ≤ 2 с) и делает Этап 2
нереализуемым.

### 3.3. Требование
Вычисление позиции должно быть **амортизированно O(1) на событие**.

### 3.4. Решение (эталонный подход)
Хранить в `XmlReader` счётчики `line`, `column` и `scanned: usize`, отражающие
позицию `scanned`; продвигать их ровно один раз по каждому байту.

```rust
struct XmlReader {
    // ...
    scanned: usize,   // до какого байта line/column уже посчитаны
    line: u32,
    column: u32,
    event_line: u32,  // локация начала текущего события (кэш)
    event_col: u32,
}

impl XmlReader {
    /// Продвигает line/column по data[self.scanned..target]. Суммарно O(n) за весь документ.
    fn advance_to(&mut self, target: usize) {
        let target = target.min(self.data.len());
        let start = self.scanned;
        if target <= start { return; }
        for &b in &self.data[start..target] {
            if b == b'\n' { self.line = self.line.saturating_add(1); self.column = 1; }
            else { self.column = self.column.saturating_add(1); }
        }
        self.scanned = target;
    }

    // в read_parsed(): в начале
    //   self.event_start = self.pos; self.advance_to(self.event_start);
    //   self.event_line = self.line; self.event_col = self.column;
    fn location(&self, _offset: usize) -> SourceLocation { // становится O(1)
        SourceLocation::new(self.part.clone(), self.event_line, self.event_col, self.event_start as u64)
    }
}
```
Допустимы эквивалентные варианты (ленивое вычисление только при ошибке с
хранением `(line,col)` на событие). Главное — отсутствие сканирования от 0.

### 3.5. Критерии приёмки R1
- Рост времени разбора линейный: при удвоении `n` время растёт ≤ ~2.3× (не ~4×).
- 1 МБ XML (n≈32000) разбирается **≤ 150 мс** на референсном оборудовании
  (текущее — 67.9 с; ориентир — ускорение ≥ 100× на этом входе).
- Значения `SourceLocation` остаются корректными (line/column совпадают с
  позементным эталоном); добавить отдельный тест на позиции.
- `last_event_location()` и все ошибки (`InvalidXml`, `UnboundPrefix`,
  `LimitExceeded`) содержат корректные локации.

## 4. P1 — R3–R7

### R3. Фича `strict-limits` (M1)
`strict-ooxml-core/Cargo.toml:17` объявляет `strict-limits`, но `cfg(feature)`
нигде не используется; README заявляет, что лимиты включаются этой фичей.
**Требование:** выбрать одно:
- (a) реализовать гейт: при выключенной фиче `ResourceLimits::default()`
  возвращает «безлимитные» значения либо лимиты становятся opt-in; **или**
- (b) удалить фичу и поправить README/доки.

Рекомендация: **(b)** — лимиты безопасности не должны быть отключаемы сборкой;
оставить их всегда включёнными. Проверить `docs.rs` metadata.
**Критерий:** нет «мёртвой» фичи; документация соответствует поведению.

### R4. `RawNormalizer` seam (M2)
`normalize/mod.rs:3-6` утверждает, что seam вызывается между OPC-парсингом и
разрешением имён, но `opc/mod.rs::open_archive` его не вызывает;
`OpenOptions.normalization` инертен. **Требование:** выбрать одно:
- (a) реально вызывать `normalize_part` при чтении каждой части (через точку
  доступа к байтам) — корректная интеграция под Этап 6; **или**
- (b) честно задокументировать seam как «зарезервировано, не подключено» и
  убрать вводящий в заблуждение doc-комментарий.

Рекомендация: **(a)** — иначе Этап 6 потребует переделки доступа к частям.
**Критерий:** либо `normalize_part` вызывается (тест с кастомным нормализатором,
переворачивающим байты, доказывает факт вызова), либо доки приведены в
соответствие и добавлен `#[doc(hidden)]`/пометка.

### R5. Лимит на входной сжатый размер (M3)
`opc/mod.rs:105` — `reader.read_to_end(&mut data)` без ограничения: многогигабайтный
архив = неограниченная аллокация. **Требование:** добавить в `ResourceLimits`
поле `max_compressed_input: u64` (дефолт, напр., 512 MiB) и читать вход через
ограничивающий reader (`Read::take` + проверка достижения предела → `LimitExceeded
{ kind: CompressedInput }`). Добавить `LimitKind::CompressedInput`.
**Критерий:** тест «архив размером > лимита → `LimitExceeded`»; лимит
переопределяется через `OpenOptions`.

### R6. Тесты и ADR (M4)
- `opc/zip.rs`: нет тестов ZIP64, bad CRC, пустого архива, усечённого файла,
  `UnsupportedCompression`, store/deflate-границ. ADR-0001 «Validation»
  заявляет их наличие.
- `xml`: нет теста `xml:space` (заявлен в ADR-0002/0003).
**Требование:** либо добавить заявленные тесты, либо скорректировать ADR.
Рекомендация: **добавить тесты**, в первую очередь ZIP64 (ветка полностью
непокрыта, покрытие `zip.rs` 72.5% строк / 48.9% функций).
**Критерии:**
- unit-тесты: ZIP64 (EOCD-сентинелы `0xFFFF/0xFFFFFFFF` + ZIP64 extra),
  bad CRC, пустой архив, усечение, `UnsupportedCompression`;
- покрытие `opc/zip.rs` ≥ 80% строк;
- тест, что `xml:space` доступен как атрибут в XML-namespace.

### R7. Conformance без полной распаковки (M5, P2)
`opc/mod.rs:330-349` (`root_namespace` → `read_part`) полностью распаковывает
`document.xml`, `styles`, `settings`, `fontTable`, `theme` ради корневого
namespace. **Требование:** определять namespace из ограниченного префикса части
(например, первых 64 КиБ) через потоковый `open_part`, без материализации всей
части; при неудаче — безопасный fallback на полное чтение.
**Критерий:** на документе с большим `document.xml` объём чтения при открытии
сокращается; тесты conformance (Strict/Transitional/Mixed) остаются зелёными.

- **R10 (P2).** Протокол fuzz: зафиксировать условия и результаты 24-часового

### 6.3. Детальный разбор

**P1 — `location()` (P0).** См. R1. Доминирующий фактор: подтверждено
квадратичным ростом. Первым делом чинить и перемерять — возможно, остальные
пункты дадут заметный эффект только после этого.

**P2 — conformance читает части целиком (P1).** `root_namespace` читает весь
`document.xml`/`styles`/`theme` ради первого `StartElement`. Для медиа-тяжёлых
или длинных документов это лишняя полная декомпрессия при каждом открытии.
Решение: потоково читать префикс части (~64 КиБ) и останавливаться на первом
элементе; анализировать только главную часть (и, при необходимости, рел-типы),
а `styles/numbering/settings` — по префиксу. Ожидаемо убирает доминирующую часть
времени открытия.

**P3 — двойная копия байтов в `decode_input` (P1).** `XmlReader` владеет
`Vec<u8>`, а `decode_input` делает `bytes.to_vec()` даже для чистого UTF-8.
Так как вызывающий уже владеет `Vec<u8>` (из `read_part`), получаем два
выделения и две копии на часть. Решение: принимать владение
(`XmlReader::from_vec(Vec<u8>)` / `Cow`) и в UTF-8-быстром пути не копировать.
Экономия — 1 memcpy размера части (существенно для `document.xml` на МБ).

**P4 — `Arc::from(data)` копирует архив (P1).** `Arc<[u8]>::from(Vec<u8>)`
выделяет новый блок и копирует всё содержимое; `Arc::new(vec)` копирует только
дескриптор `Vec`. Решение: хранить `Arc<Vec<u8>>` (доступ через `&arc[..]`)
либо читать сразу в нужный контейнер. Экономия — один memcpy размера архива.

**P5 — CRC-32 побитовый (P1).** `crc32_update` считает 8 итераций на байт.
CRC выполняется по **всем** распакованным байтам (включая media). Замена на
табличный CRC-32 (IEEE) с предвычисленной таблицей 256×u32 даёт ~4–6× на этой
функции и заметна на больших частях. Таблица — `static` через `OnceLock`/
`LazyLock` либо `const fn`-таблица.

**P6 — реконструкция `quick_xml::Reader` на каждое событие (P2).**
`xml/mod.rs:155`: `Reader::from_reader(&self.data[start..])` создаётся на каждый
`next_event`, что даёт аллокацию/инициализацию на событие. После фикса P1
измерить; если вклад существенен — перейти на один персистентный Reader.
Без self-reference и без `unsafe` это делается так: хранить буфер в
`Arc<[u8]>`, а Reader создавать над `&self.data[..]` один раз на весь документ,
продвигаясь по нему; владение буфером в `Arc` + заимствование в методе
`next_event` возможно, если Reader создаётся внутри вызова, но тогда снова
per-event. Практичный компромисс без self-ref/`unsafe`: разбить чтение на
ограниченные окна (Reader над окном, при исчерпании — следующее окно), что
сокращает число конструкций. Решение принимать по результатам бенчмарка, не
преждевременно.

**P7 — двойные `Vec` на атрибуты (P2).** `parse_start` собирает
`Vec<(String,String)>`, затем `open_element` строит ещё `Vec<Attr>`. Можно
резолвить атрибуты в один проход/один `Vec`. Небольшой, но на каждый элемент.

**P8 — `NsStack::resolve` линейный (P3).** Скан bindings от конца на каждое имя.
Практически namespace-ов мало и они у корня — эффект мал. Оставить; при
усложнении (много локальных `xmlns`) — перейти на map-per-scope.

**P9 — `String` на каждое имя (P3).** Следствие ADR-0003 (owned events).
На Этапе 1 приемлемо; на Этапе 2 (DOM) рассмотреть интернирование локальных
имён (арена/symbol table), чтобы не аллоцировать повторы `w:p`, `w:r` и т.п.

### 6.4. Что оптимизировать НЕ стоит сейчас
- `parallel`/rayon: до появления нескольких тяжёлых независимых частей (Этап 2)
  преждевременно.
- Векторизация `location`/парсера: не нужно после P1.
- Замена `quick-xml`: оправдана только если P6 покажет регресс; иначе риск
  для безопасности/сроков выше выигрыша.

### 6.5. Бенчмарки и защита от регрессий
Добавить `strict-ooxml-core/benches/` (`criterion`, dev-dep):
1. `xml_scan` — разбор N=1k/8k/32k/128k элементов (`<w:p><w:r><w:t>`); проверяет
   линейность (P1).
2. `xml_deep` — глубокая вложенность (проверка `max_xml_depth` без обвала).
3. `opc_open` — открытие синтетического `.docx` (3 и 50 частей), проверяет P2.
4. `part_read` — чтение stored/deflate части 1/10 МБ, проверяет P3/P5 (CRC).
5. `crc32` — пропускная способность.

В CI: `cargo bench --bench <name> -- --test` (smoke) + сохранение baseline;
пороговый тест «1 МБ XML ≤ X мс» как регрессионный барьер (можно как
`#[test]` с щедрым порогом, чтобы не флакать на CI).

## 9. Приложение А. Стенд для замера K1

Воспроизведение (release):
```rust
// временный бинарник, зависимость: strict-ooxml-core = { path = "..." }
let mut xml = String::from("<w:document xmlns:w=\"urn:w\">");
for _ in 0..n { xml.push_str("<w:p><w:r><w:t>x</w:t></w:r></w:p>"); }
xml.push_str("</w:document>");
let mut r = XmlReader::new(&xml.into_bytes(), PartId::new("/word/document.xml"),
                          &ResourceLimits::default())?;
let t = Instant::now();
while r.next_event()? != XmlEvent::Eof {}
println!("{n}: {:?}", t.elapsed());
```
