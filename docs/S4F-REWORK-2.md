## 1. Проблема B-1 (основная). `w:docGrid/@w:linePitch` не применяется при
заданном интервале

**Факт.** Высота строки по сетке включается только при отсутствии явного
интервала: `strict-ooxml-render-svg/src/layout/paragraph.rs`,
`resolve_line_metrics`, ветка `Some(pitch) if computed.line_pt.is_none()`. Но
реальные документы (и сам `strict-text.docx`) задают одинарный интервал
`w:spacing w:line="240" w:lineRule="auto"` (в `docDefaults` и стиле `Normal`).
Тогда `computed.line_pt = Some(12.0)`, и `docGrid` **игнорируется**, хотя WPS его
применяет.

**Контролируемый эксперимент (воспроизведено при приёмке).** В
`strict-ooxml-core/tests/strict/strict-text.docx` добавлен
`<w:docGrid w:type="lines" w:linePitch="360"/>` в `w:sectPr`; сгенерирован
эталон WPS:

| Рендер | y-центры текстовых полос | SSIM vs WPS |
|---|---|---|
| WPS (эталон, grid) | `137, 181, 205, 228, 252, 276, 301, 323` (шаг 24 px) | — |
| наш (grid + `line=240`) | `126, 156, 174, 191, 208, 223, 241, 261` (как без grid) | **0.9187 < 0.95** |

Удаление `w:line="240" w:lineRule="auto"` из фикстуры смещает наши центры на шаг
24 px (`162, 186, 210, …`) — это подтверждает, что причина именно в условии
`line_pt.is_none()`.

**Почему тесты не поймали.** Ни один закоммиченный эталон не покрывает этот путь:
`strict-text` не содержит `docGrid`; у `strict-profile` grid влияет на позиции,
но проверяется **только число страниц** (per-pixel SSIM для него не выполняется).

**Связанное B-1b (причина второго порядка).** `strict-ooxml-render-svg/src/style.rs`,
`compute_paragraph` применяет только стиль абзаца (`Normal`/`basedOn`) и прямые
свойства, но **не читает `docDefaults`/`pPrDefault`**. Поэтому `strict-profile`
(интервал задан только в `docDefaults`, `w:line="12.95pt"`) получает
`line_pt=None`, и grid у него включается — случайно. Если исправить B-1b
(начать каскадить `docDefaults`) **до** B-1, `strict-profile` потеряет grid и
может изменить пагинацию. Требуется согласованное решение.

**Требование B-1.**
1. `docGrid/@w:linePitch` должен применяться и при `w:lineRule="auto"` с
   заданным `w:line` (одинарный интервал) — как это делает WPS. Условие
   `line_pt.is_none()` не должно быть единственным триггером; обосновать
   правило (например, grid применяется при `lineRule=auto`, если документ
   объявил линию-сетку, независимо от множителя).
2. Учесть взаимодействие с B-1b: каскад `docDefaults` (`pPrDefault` spacing) —
   либо реализовать, либо явно и обоснованно задокументировать, почему
   `docDefaults` не каскадируется; в любом случае поведение `strict-profile`
   (2 стр.) не должно регрессировать.
3. Закрепить поведение фикстурой: добавить Strict-документ с `docGrid`
   (`strict-text-grid.docx` или эквивалент) + WPS-эталон и включить его в SSIM.

**Критерии приёмки B-1.**
1. На новой grid-фикстуре с `w:line="240" w:lineRule="auto"` позиции строк
   совпадают с WPS в пределах допуска SSIM: **SSIM ≥ 0.95** и число страниц =
   эталону.
2. `strict-text` (без grid) и `strict-profile` (2 стр.) — без регрессий
   (SSIM/пагинация не хуже текущих: 0.9768 и 2/2).
3. Эталон grid-фикстуры сгенерирован на **пиннингованной** WPS `12.1.0.28485`,
   закоммичен с атрибуцией и SHA-256; WPS в CI не требуется.
4. Обновлены `refs/README.md`, `docs/stage-4-report.md`, ADR-0006 (описание
   правила grid).

## 2. Проблема B-2 (существенная). Нет SSIM по реальному Strict

**Факт.** Критерий S4F §4.2 требует SSIM ≥ 0.95 на наборе «**≥ 1 реальный
Strict** + синтетические». Реально `tests/ssim.rs` (`SSIM_DOCS`) гейтит только
`strict-text` (синтетический). Единственный реальный Strict —
`strict-profile.docx` — под SSIM **не** проверяется:

| Документ | Кадр | SSIM (внешне) | ink (наш) |
|---|---|---|---|
| `strict-profile/page_1` | 727×1055 | 0.9132 | **0.00 %** |
| `strict-profile/page_2` | 727×1055 | 0.9352 | **0.00 %** |

Наш рендер реального Strict — практически **пустой** (единственный `w:t` лежит
внутри text box; charts/diagrams не растеризуются; выводятся только серые
плейсхолдеры). Совпадение «2/2 страницы» получено за счёт резервирования
extent, но визуальной приёмки на реальном документе нет.

**Требование B-2** (выбрать один путь и оформить):
- **(A)** добавить ≥ 1 **реальный Strict-текстовый** документ (с текстом в
  теле, без зависимости от chart/diagram) + WPS-эталон и включить его в
  `SSIM_DOCS` (порог 0.95, инвариант страниц); либо
- **(B)** письменно зафиксировать у заказчика, что реальный Strict проверяется
  **только по числу страниц** (обосновать ограничениями Stage 4), и **снять**
  формулировку «O1 закрыт» до появления SSIM-покрытия реального Strict.

**Критерии приёмки B-2.**
1. Либо в наборе SSIM присутствует реальный Strict с SSIM ≥ 0.95 и инвариантом
   страниц; либо в `STAGE-4-ACCEPTANCE.md`/ADR-0006 зафиксировано согласованное
   исключение с явной формулировкой статуса (не «закрыто»).
2. `STAGE-4-ACCEPTANCE.md` §4 O1 и заголовок статуса приведены в соответствие
   фактическому покрытию (сейчас заголовок «ПРИНЯТО УСЛОВНО», а O1 помечен
   «ЗАКРЫТО»).

## 3. Проблема B-3 (значимая). SSIM-гейт слабо различает корректный и
некорректный рендер

**Факт (внешние замеры, skimage, 11×11, σ=1.5).**

| Сравнение с эталоном `strict-text` | SSIM |
|---|---|
| наш рендер (базовый) | 0.9768 |
| пустая белая страница | **0.9475** (порог 0.95 — запас 0.0025) |
| сдвиг текста на 2 px по вертикали | 0.9508 (проходит) |
| сдвиг текста на 3 px по вертикали | 0.9473 (падает) |
| сдвиг по горизонтали 3…10 px | 0.9516…0.9531 (проходит) |

На разреженном тексте (ink ≈ 0.9 %) интегральный SSIM почти не наказывает
пропажу/сдвиг контента: пустая страница не проходит лишь на 0.0025, а
горизонтальный сдвиг до ~10 px гейт не ловит.

**Требование B-3.** Дополнить гейт чувствительным инвариантом, который
детерминирован и не зависит от растеризатора, например:
- число текстовых полос (строк) = эталону и y-центры полос в пределах **±1 px**
  от эталона (на `strict-text` это уже выполняется: 8/8, ±1 px); и/или
- порог normalized cross-correlation (NCC) для области текста; и/или
- порог на долю «чернил» (ink fraction) с допуском.

**Критерии приёмки B-3.**
1. Контроль-тест: **пустая белая страница отклоняется**; сдвиг текста ≥ 3 px
   отклоняется; корректный рендер проходит.
2. Инвариант детерминирован и проходит на всех утверждённых документах.
3. Обоснование выбора метрики зафиксировано в `docs/`/ADR.

## 4. Проблема B-4 (мелкая). Устаревший модульный doc в `font/metrics.rs`

**Факт.** `strict-ooxml-render-svg/src/font/metrics.rs` (шапка, строки 2–6)
утверждает: «Real glyph advance widths are not bundled in Stage 4… the builtin
provider uses a deterministic per-character-class model». Это противоречит
факту: реальные метрики читаются из бандл-шрифтов через `skrifa`, а модель
классов — только fallback.

**Требование/критерий.** Привести doc в соответствие с реализацией (модель
классов — fallback для неизвестных семейств и отсутствующих глифов).

## 5. Проблема B-5 (мелкая). Неточность `refs/README.md`

**Факт.** В таблице генератора: «DPI / page size | 96 DPI; page size from

при проверке инвариантов.

**Требование/критерий.** Уточнить: размеры по документам (`strict-text`
816×1056; `strict-profile` 727×1055).

## 6. Проблема B-6 (мелкая, тесты). Частично вакуумная проверка бандла

**Факт.** `builtin_advances_match_known_metrics` проверяет для Cambria/Arial/
Times/Courier только `width_scale == 1.0`, но `family_scale` также равна 1.0 для
Cambria/Tinos — значит для Calibri/Cambria/Tinos тест **не доказывает**, что
шрифт реально забандлен. `Caladea` (Cambria) не покрыт ни golden, ни SSIM —
визуально не проверяется нигде.

**Требование/критерий.**
1. Проверка бандла должна быть невакуумной: для каждого из 5 семейств
   убедиться, что взят именно бандл-шрифт (например, сравнить advance
   характерного глифа с ожидаемым значением, отличным от fallback-модели).
2. Обеспечить визуальное/структурное покрытие `Caladea` (Cambria) — в
   фикстуре/golden/SSIM.
