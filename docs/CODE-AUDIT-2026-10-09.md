# Аудит кода: найденные ошибки, ранжированные по серьёзности

**Дата:** 9 октября 2026
**Ветка / SHA:** `master` @ `5da50ed`
**Предмет:** `strict-ooxml-core` (OPC, ZIP, XML, нормализатор) и
`strict-ooxml-wml` (парсер), плюс PDF-пути, где они пересекаются.
**Метод:** статический разбор с построчными ссылками, трассировка реальных путей
вызова от `Package::open_*`. Кода не писалось, тесты не запускались.
**Статус:** аудит завершён, правок не вносилось.

---

## 0. Краткий вывод

Код в целом аккуратен в том, что касается границ: смещения полей ZIP сверены с
APPNOTE, инкрементальный CRC математически корректен, все сравнения лимитов
используют правильный оператор, достижимых `unwrap`/`expect`/индексаций вне
тестовых модулей нет.

Найдено **19 дефектов**, из них 4 высокой серьёзности. Все четыре сосредоточены в
`strict-ooxml-core/src/normalize/transitional.rs` — нормализаторе
Transitional → Strict, который пишет по 4700 строк и является самой сложной
частью конвейера. Три из них дают **молчаливую потерю или порчу содержимого на
валидном входе**, четвёртый — невалидный выход, помеченный как успешный.

Общий класс: модуль завязал на «плоский» учёт состояния там, где нужна
область видимости. Таблица префиксов, множество отброшенных объявлений и стек
счётчика математики — три независимых экземпляра одной ошибки.

## 1. Высокая серьёзность

### 1.1. `drain_textbox_content` теряет CDATA внутри VML-текстбокса

**Где:** `strict-ooxml-core/src/normalize/transitional.rs:710`

```rust
Event::Empty(_) | Event::Text(_) if depth > 0 => out.push(event.clone()),
_ => {}
```

**Почему это ошибка.** У `Event::CData` нет отдельной ветки, и он попадает в
`_ => {}`, то есть молча выбрасывается. Собранные события — это то, что
`rewrite_legacy_graphics` (строки 529-531) передаёт обратно через `rewrite_event`,
чтобы они стали телом `wps:txbx/w:txbxContent`. Любой символьный текст, отданный
как CDATA внутри текстбокса, до writer'а не доходит.

**Вход (валидный XML, Transitional):**

```xml
<w:document xmlns:w="http://schemas.openxmlformats.org/wordprocessingml/2006/main"
            xmlns:v="urn:schemas-microsoft-com:vml">
 <w:body><w:p><w:r><w:pict><v:shape type="#_x0000_t202" style="width:200pt;height:60pt">
  <v:textbox><w:txbxContent><w:p><w:r><w:t><![CDATA[in the box]]></w:t></w:r></w:p></w:txbxContent></v:textbox>
 </v:shape></w:pict></w:r></w:p></w:body></w:document>
```

**Наблюдаемый результат:** `<wps:txbx><w:txbxContent></w:txbxContent>` — текст
исчез. `LossRecord` не заводится, и `verify_no_silent_loss` проходит, потому что
ни один узел не был посчитан удалённым. Это ровно тот режим отказа, ради
существования которого модуль и написан.

**Подтверждение.** Ближняя копия этого же обхода,
`vml::textbox_children` (`strict-ooxml-core/src/normalize/vml.rs:741-745`),
имеет catch-all `_ => { if depth > 0 { out.push(...) } }`, который CDATA
сохраняет. Две копии одного обхода, одна теряет CDATA, другая нет.

**Покрытие тестами.** `a_vml_text_box_becomes_a_shape_that_still_has_its_text`
(строка 3233) использует только обычный `<w:t>`. Путь через `v:group` идёт
через `vml::textbox_children`, который CDATA сохраняет, поэтому групповая
фикстура поймать это не может.

**Уверенность:** подтверждено чтением.

### 1.2. Таблица префиксов `PartContext` без области видимости

**Где:** `strict-ooxml-core/src/normalize/transitional.rs:1556, 1770-1776`

```rust
fn remember_prefix(&mut self, prefix: Vec<u8>, uri: String) {
    if let Some(slot) = self.prefixes.iter_mut().find(|(known, _)| *known == prefix) {
        slot.1 = uri;              // перезапись; pop не существует
    } else {
        self.prefixes.push((prefix, uri));
    }
}
```

**Почему это ошибка.** Структура `PartContext` хранит `prefixes: Vec<(Vec<u8>, String)>`.
Стек отметок отсутствует, при закрытии элемента привязка не снимается. `uri_for`
(строка 1778) и `prefix_for` (строка 1814) читают эту одну плоскую таблицу.
Читатель `XmlReader` делает то же самое правильно — `NsStack::push_scope` /
`pop_scope` с массивом `marks` (`strict-ooxml-core/src/xml/ns_stack.rs:38-47`).

**Вход (валидный XML):**

```xml
<w:document xmlns:w="http://schemas.openxmlformats.org/wordprocessingml/2006/main" xmlns:p="urn:outer">
 <w:body>
  <w:p xmlns:p="urn:inner"><w:r><w:t>x</w:t></w:r></w:p>
  <p:tag/>
 </w:body></w:document>
```

**Наблюдаемый результат.** После `</w:p>` таблица по-прежнему хранит `p` → `urn:inner`,
поэтому `<p:tag/>` резолвится в `urn:inner`. `apply_rewritten_element_name`
(строка 1067) видит, что `uri_for("p") == Some("urn:inner") == element_uri`,
сохраняет префикс и пишет `<p:tag/>` без объявления `xmlns:p` — а в выходе `p`
означает корневой `urn:outer`. Два неверных пространства имён, выданные молча.

**Разрушающий вариант.** Если внутреннее переобъявление указывает на
Transitional URI WML, то все последующие элементы с префиксом `p` считаются WML,
проходят `map_uri` → Strict WML и получают переименования T3 и карты значений T4,
которые им не полагаются.

**Покрытие тестами.** `sibling_namespace_declarations_stay_on_each_sibling`
(строка 3344) выглядит как покрытие, но им не является: оба его соседа префикс
переобъявляют, а именно этот случай `remember_prefix` и обрабатывает. Теста, где
предок объявляет префикс, а более поздний сосед его лишь использует, нет.

**Уверенность:** подтверждено чтением.

### 1.3. `check_invariants` ищет байты `mc:I` по всему выходу

**Где:** `strict-ooxml-core/src/normalize/transitional.rs:1244`

```rust
if output.windows(4).any(|window| window == b"mc:I") {
    violations.push(
        "an mc:Ignorable survived T6; Strict conformance is defined on the post-MCE part \
         (ECMA-376 Part 1 §2.1 clause (ii))".to_owned(),
```

**Почему это ошибка.** Сырое 4-байтовое окно по всему выходу, включая текстовые
узлы, CDATA и значения атрибутов. Любой документ, в **содержимом** которого
встречается строка `mc:I`, подпадает под проверку.

**Вход (валидный Transitional):**

```xml
<w:document xmlns:w="http://schemas.openxmlformats.org/wordprocessingml/2006/main">
 <w:body><w:p><w:pPr><w:jc w:val="left"/></w:pPr>
  <w:r><w:t>strip mc:Ignorable before going Strict</w:t></w:r></w:p></w:body></w:document>
```

**Наблюдаемый результат.** `T4.value` срабатывает на `left` → `start`, поэтому
`transformed` истинно, `check_invariants` выполняется, скан попадает на прозу.
Под `InvariantMode::Strict` функция `normalize` возвращает
`Err(NormalizationInvariantViolation)` на совершенно валидной Transitional-части.
Под дефолтным `Lenient` заводится ложная запись `T8.invariant`, которая затем
попадёт в census named-loss.

**Подтверждение.** Это в точности тот дефект, который AUD-32 устранил для
соседней проверки: `namespace_declarations` (строка 1285) переписали на разбор
через `quick_xml` с комментарием «чтобы текстовый `xmlns` в содержимом элемента
не давал ложного срабатывания». Проверка `mc:I` осталась в текстовой форме.

**Уверенность:** подтверждено чтением.

### 1.4. T7 конвертирует обрезанное поддерево `w:pict` и возвращает небалансный XML как успех

**Где:** `strict-ooxml-core/src/normalize/transitional.rs:1490, 1501-1507, 368-376`

```rust
fn next(&mut self) -> Option<Event<'static>> {
    if let Some(event) = self.buffered.pop_front() { return Some(event); }
    self.reader.read_event().ok().map(into_owned_event)   // Err -> None
}
...
while depth > 0 {
    let Some(event) = source.next() else { break };      // и Eof -> break
```

**Почему это ошибка.** Политика «повреждённый вход оставить ровно как есть»
(комментарий и код на строках 330-355) достигается только при `Err` в **главном**
цикле. Документ, обрезанный по границе тега, даёт `Ok(Event::Eof)`, который
`collect_subtree` обрабатывает точно так же, как ошибку: возвращает частичное
поддерево, и `rewrite_legacy_graphics` классифицирует его всё равно —
`vml::classify` требует лишь найти `v:imagedata`.

**Вход** — любой Transitional-файл, обрезанный посреди `w:pict`:

```xml
<w:document xmlns:w="...2006/main" xmlns:v="urn:schemas-microsoft-com:vml" xmlns:r="...relationships">
 <w:body><w:p><w:r><w:pict><v:shape type="#_x0000_t75" style="width:100pt;height:50pt">
 <v:imagedata r:id="rId1"/>
```

**Наблюдаемый результат.** `normalize` возвращает `Ok(Cow::Owned(..))`, содержащий
конвертированный `<wp:inline>` и все открытые предки без единого закрывающего
тега. Отчёт утверждает `T7.vml-shape: 1` при `lossy_count == 0` — чистая
конвертация половины документа.

**Почему `check_invariants` это не поймает.** `namespace_declarations` (строка
1285) прерывается на `Err(_)`, то есть на невалидном XML разбор молча
останавливается.

**Подтверждение.** Док-комментарий на строке 1498 утверждает: «обрезанное
поддерево — не картинка, которую кто-то должен рисовать, и не ветка, которую
кто-то должен разворачивать» и что стадии его «отклоняют». Они этого не делают:
у `classify` нет проверки полноты. Либо `collect_subtree` должен помечать
усечение и вызывающие должны отказывать, либо `normalize` должен проверять
балансировку своего выхода.

**Уверенность:** подтверждено чтением.

## 2. Средняя серьёзность

### 2.1. `ZipWriter::add_part` не откатывает свой счётчик на пути ошибки

**Где:** `strict-ooxml-core/src/opc/zip/write.rs:141-149`

```rust
// Saturating: the limit check right after still refuses.
self.total = self.total.saturating_add(data.len() as u64);
if self.total > self.limits.max_total_uncompressed {
    return Err(StrictError::LimitExceeded { .. });   // self.total НЕ восстановлен
}
self.entries.push((name, data));
```

**Почему это ошибка.** `self.total` мутируется **до** проверки, которая может
отклонить, а ранний возврат отмену не делает. Это единственное место в ZIP-слое,
где ошибка оставляет мутированное состояние. Отклонённая часть навсегда завышает
рабочий итог, и каждая последующая `add_part` измеряется против суммы, включающей
байты, которые никогда не были записаны.

**Воспроизведение:**

```rust
let limits = ResourceLimits { max_single_uncompressed: 16, max_total_uncompressed: 10,
                              max_zip_entries: 8, ..Default::default() };
let mut w = ZipWriter::with_limits(limits);
w.add_part(&PartId::new("/a"), vec![0u8; 6]).unwrap();          // total = 6   OK
assert!(w.add_part(&PartId::new("/b"), vec![0u8; 8]).is_err()); // 14 > 10, total := 14
// total теперь 14, хотя в writer только 6 байт:
assert!(w.add_part(&PartId::new("/c"), vec![0u8; 4]).is_err()); // 18 > 10
//   ^ НЕВЕРНО: истинный итог 6 + 4 = 10, что в точности вписывается.
```

**Почему это не ловится тестом.** `entry_and_size_limits_are_enforced`
(`write.rs:439`) падает на `max_zip_entries` (строка 126, проверяется **до**
обновления итога), а его первая ошибка — на `max_single_uncompressed`
(строка 134, тоже до).

**Оценка.** Не эксплуатируемо для памяти или DoS — направление отказа
fail-closed — но даёт неверный результат: легитимная запись отвергается после
восстановимой ошибки. Только на пути записи, не из враждебного входа, поэтому
средняя, а не высокая.

**Уверенность:** подтверждено чтением.

### 2.2. Распознавание `.rels` / `_rels` регистрозависимо, вопреки собственному правилу `PartId`

**Где:** `strict-ooxml-core/src/opc/mod.rs:203`, `strict-ooxml-core/src/opc/rels.rs:455, 461`

```rust
// opc/mod.rs:203
if !entry.id.as_str().ends_with(".rels") { continue; }
// opc/rels.rs:455
let (dir, file) = path.rsplit_once("/_rels/")?;
// opc/rels.rs:461
let source_name = file.strip_suffix(".rels")?;
```

**Почему это ошибка.** `Eq`/`Hash`/`Ord` у `PartId` явно ASCII-регистронезависимы
(`strict-ooxml-core/src/part.rs:52-92`), и `opc/path.rs:84-91` формулирует правило,
на котором построен модуль: «имена записей ZIP — это буквальные байты, которые
сравнивает OPC», при этом `part.rs:23-30` говорит, что имена частей «сравниваются
без учёта регистра ASCII». Значит `word/_RELS/document.xml.rels` — по
собственным правилам крейта та же часть, что `word/_rels/document.xml.rels`, но
молча пропускается как обычная.

**Вход:** запись, записанная как `word/_RELS/document.xml.rels`
(`_RELS` заглавными, `.rels` строчными).

**Наблюдаемый результат.**
1. `opc/mod.rs:203` — проверка проходит (`ends_with(".rels")` истинно).
2. `rels.rs:455` — `rsplit_once("/_rels/")` возвращает `None`.
3. `continue` — связи уровня пакета никогда не читаются.
4. `locate_main_document` (`opc/mod.rs:479-494`) ничего не находит и возвращает
   `InvalidZip("package has no officeDocument relationship")`.

Показательно сравнение: `[Content_Types].xml` находится регистронезависимо,
потому что идёт через `zip.entry()` — то есть через `PartId`-ключевую карту
(`opc/zip/mod.rs:135-137`), а не через сырой строковый тест. Тот же класс поиска,
два разных механизма, один из них неверен.

**Уверенность:** несогласованность подтверждена чтением. Слабое место — вопрос о
том, требует ли OPC регистронезависимого опознания `_rels` (ECMA-376 Part 2
§10.1.2.2 обычно читают как «сравнивать имена частей без учёта регистра ASCII», и
крейт уже принял это правило в двух других местах). Внутреннее противоречие
точно: `PartId` говорит, что это одна часть, а сканер `.rels` — что нет.

### 2.3. `write_start_markup` молча снимает пространство имён с любого атрибута вне четырёх известных префиксов

**Где:** `strict-ooxml-wml/src/parse/drawing.rs:2262-2270`

```rust
let attr_prefix = markup_prefix(attr.name.ns.as_ref().map(NsUri::as_str));
out.push(' ');
if let Some(prefix) = attr_prefix {
    // Unprefixed attributes stay unprefixed (XML Namespaces).
    if attr.name.ns.is_some() { out.push_str(prefix); out.push(':'); }
}
out.push_str(attr.name.local());
```

**Почему это ошибка.** `markup_prefix` (строка 2390) знает только `lc`, `a`, `r`,
`pic`, `xml`. Атрибут в любом другом пространстве — `w:val`, `wps:cNvPr`,
собственный префикс производителя — проваливается сквозь `if let` и пишется как
**неквалифицированное** имя. `w:val="x"` становится `val="x"`: другой атрибут, в
никаком пространстве, значение на месте.

То же самое происходит с элементами на несколько строк выше (строки 2236-2241):
`w:`-элемент внутри `lc:lockedCanvas` пишется как голое локальное имя, то есть
целое чужое поддерево внутри канвы перевыдаётся без пространств имён.

**Подтверждение.** Соседний сериализатор `capture_fragment` в идентичной
ситуации поступает правильно: `prefix_of` возвращает `None` для неизвестного
пространства, и функция возвращает `Ok(None)` (`drawing.rs:820-828, 843-845,
853-855`). `write_start_markup` деградирует молча.

**Достижимость.** Через любое поддерево `lc:lockedCanvas`, содержащее элемент или
атрибут в пространстве `w:` либо в пространстве производителя:
`capture_locked_canvas` сериализует поддерево целиком без фильтрации
(`drawing.rs:634-679`).

**Уверенность:** подтверждено чтением.

## 4. Что проверено и оказалось чистым

### Смещения и CRC в ZIP

- **Все смещения полей пересчитаны против APPNOTE** и верны: EOCD `+10/+12/+16`;
  центральный заголовок `+8/+10/+16/+20/+24/+28/+30/+32/+42`, имя на `+46`;
  локальный заголовок `+26/+28`, данные на `+30`; ZIP64 EOCD `+32/+40/+48`;
  ZIP64 локатор `+8`, по адресу `eocd-20`. Ни одного смещения на единицу.
- **Инкрементальный CRC математически корректен.** `crc32_update` имеет форму
  `!R(!crc, data)`, и для chaining выполняется тождество
  `f(f(0, a), b) == f(0, a‖b)`, поскольку две инверсии сокращаются. Поэтому
  использование в `PartReader::read` (`mod.rs:614`) корректно, как и однократный
  `crc32_update(0, data)` в `ZipWriter::finish` (`write.rs:175`).
- **CRC считается по ровно правильному отрезку** — `window[..n]`, то есть по
  фактически выданным байтам, что верно и для `Stored` (копирование), и для
  `Deflate` (счётчик записи инфлятора).
- **Обработка позиционных слотов ZIP64 верна.** `take(false)` возвращает `None`
  **не** продвигая `p`, поэтому writer, перенесший в ZIP64 только смещение, не
  утекает смещение в `uncompressed_size` (`mod.rs:400-411`). Короткое тело
  возвращает `None` без продвижения, поэтому нельзя занять соседний слот.
  Тесты `mod.rs:1132-1174` закрепляют все четыре формы.
- **`finish()`** сравнивает и `produced != expected_len`, и `crc != expected_crc`,
  именно в таком порядке, и достигается через `read_to_end`.

### Канонизация путей и percent-декодирование

- **`a/../b` → `/b`, `a//b` → `/a/b`, `a/./b` → `/a/b`**; `""`, `"/a"`, `".."`,
  `"a/.."`, `"."`, `"./."`, `"/"` — отвергаются (`path.rs:22-39, 141-175`;
  тесты `221-261`).
- **Выход за корень через percent-кодирование недостижим.** `%2E%2E`
  декодируется в `..` **до** `split_and_normalize`, который затем делает `pop` и
  отвергает. Вариант `Target="%2Fword%2F..%2F..%2Fsecret"` даёт `Err`;
  прослежены три варианта, все отвергнуты как «path escapes the package root».
  То, что `%2F` становится разделителем, **не** даёт обхода.
- **Обратный слэш и NUL** отвергаются глобально; `char::is_control` проверяет
  C0/C1/DEL **по сегментам после** декодирования, поэтому `%0A` в `Target` или в
  `Override/@PartName` отвергается.
- **Декодирование применяется ровно один раз и в правильных местах.** Ровно два
  места вызова: `rels.rs:511` (только внутренний `Target`) и
  `content_types.rs:65` (`Override/@PartName`). Никогда дважды. Имена записей ZIP
  идут прямо в `canonicalize_part_name` (`zip/mod.rs:72`) без декодирования — как
  и требует `path.rs:84-91`. Для `TargetMode="External"` декодирование
  пропускается (`rels.rs:495, 508-513`), так что `%25` в URL остаётся целым.
  `Relationship.target` хранит сырое написание (`rels.rs:518`), и
  `write_relationships` возвращает именно его (`rels.rs:603`).

### Сравнения лимитов и работа со стеком

- **Все счётчики инкрементируют первым и сравнивают с `>`**, так что бюджет *n*
  допускает ровно *n*: `check_depth`, `check_attributes`, `check_text`
  (`xml/safety.rs`), `Depth::enter` (`parse/depth.rs:60`), `nested_block` /
  `nested_text_box` / `nested_inline` (`parse/mod.rs:978, 1007, 1030`),
  `parse_group` (`parse/drawing.rs:2064`), `MathScope::charge_node` / `enter`
  (`math.rs:59, 65`). Поведение `max_xml_depth: 2` закреплено тестом
  `enforces_depth_limit`.
- **Ни одного достижимого `unwrap`, `expect`, `panic!`, `unreachable!` или
  прямой индексации** вне `#[cfg(test)]` в просмотренных модулях `opc/`, `xml/`,
  `normalize/transitional.rs` и парсере WML.
- **Арифметика `saturating_add`/`saturating_sub` везде**, где есть риск;
  вычитание под пеленой присутствует только в `read_prefix`
  (`opc/mod.rs:693`), где оно защищено предшествующим `while buffer.len() < limit`.
- **Ни одного бесконечного цикла на враждебном входе.** Цикл
  `Zip64Extra::parse` всегда продвигает `pos = body_end > pos`; цикл
  `Inner::Deflate::read_into` всегда продвигает `in_pos` либо возвращает `Err` при
  нулевом потреблении (`zip/mod.rs:582-587`).

### Читатель XML

- **Конфигурация `quick_xml` безопасна.** `check_end_names = false` и
  `allow_unmatched_ends = true` (`xml/mod.rs:133-134`) не позволяют просочиться
  ничему: `close_element` (строка 283) сверяет сырое имя закрытия с
  `open_names.last()` и ошибается при несовпадении, а также при пустом стеке.
  Самозакрывающиеся элементы не попадают в `open_names`, но ставят `pending_end`,
  который сливается в начале `next_event` (строка 190) **до** дальнейшего чтения,
  поэтому `<a><b/></a>` балансируется точно.
- **Дисциплина push/pop сбалансирована.** Каждому `push_scope` ровно один
  `pop_scope`: либо через `pending_end` для пустых элементов, либо через
  `close_element`. `pop_scope` усекает до отметки, поэтому привязка не может
  утечь вперёд — та самая дисциплина, которой не хватает `PartContext`.
- **Порядок резолвинга имён верный.** `close_element` вызывает `resolve_name`
  **до** `close_scope` (`mod.rs:292-293`), так что собственный `xmlns` элемента
  ещё в области видимости для его закрывающего тега. `open_element` объявляет до
  резолвинга, так что префикс, объявленный на самом элементе, резолвится —
  включая случай `xml:space`, закреплённый тестом на `mod.rs:764`.
- **Накопление `text_total`** (`mod.rs:312`) — `saturating_add` на `u64` не
  оборачивается, а `check_text` сравнивает итог, поэтому переполнение не может
  замаскировать превышенный лимит. То же для `SupportModel::count` и `merge`.
- **CDATA и комментарии** в читателе: `Event::CData` проходит дословно без
  декодирования сущностей (`mod.rs:368-373`), что верно — содержимое CDATA
  буквально. Комментарии и PI — `Parsed::Skip`. Вложенный CDATA не является
  конструкцией XML; `]]>` внутри секции завершает её в токенизаторе.
- **`normalize_encoding`** транскодирует UTF-16 и унаследованные кодировки;
  `from_vec` владеет `Vec<u8>` целиком, избегая копирования на обычном пути UTF-8.

### Прочее

- **Арифметика потолка расширения** (`transitional.rs:185-192, 393-400`) —
  `saturating_mul`/`saturating_add` на случайе `usize::MAX`, закреплено тестом
  `expansion_limit_factor_and_bytes_saturate`.
- **`method_for` и `compress` в `write.rs` взаимно согласованы** (строки 232-238 и
  220-230): `compress` возвращает `Borrowed` ровно тогда, когда
  `deflated.len() >= data.len()`, а `method_for` возвращает `Stored` ровно тогда,
  когда `compressed.len() == uncompressed_len`. Нет написания, при котором метод
  расходится с полезной нагрузкой.
- **`policy::decide` вызывается один раз** и соответствует документированной
  матрице из 20 ячеек (`policy.rs:41-73`); второй реализации гейта в просмотренных
  файлах нет.
- **Разбор чисел WML** (`parse/mod.rs:1306-1420`): суффиксы единиц матчатся точно,
  сравнения `f64::from(i32::MAX)` насыщаются в нужную сторону, `parse_decimal`
  отвергает не-конечные значения до `as i32`. Неизвестная единица возвращает
  `None` (записывается), а не неверное число.
- **Определение переполнения в `model/support.rs`** (`record:137`, `merge:170`):
  проверка бюджета зависит от порядка слияния, но источник — `BTreeMap`, поэтому
  итерация детерминирована и property-тест `overflow_collapses_past_the_budget`
  держится. Единственная неровность — у `support.overflow` `message` остаётся
  первым свёрнутым сообщением, а `status` — максимумом по всем; запись описывает
  произвольную из поглощённых характеристик. Это огрех отчётности, а не неверный
  выход.
