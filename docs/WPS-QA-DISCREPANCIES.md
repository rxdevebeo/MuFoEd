# Несоответствия рендера эталону WPS

Живой реестр расхождений нашего рендера с эталоном WPS, найденных
инструментом `xtool/wps-qa` (см. его [README](../xtool/wps-qa/README.md)).
Сюда заносится каждое расхождение, которое разобрано до причины или хотя бы до
воспроизводимого симптома. Сырые числа по всем документам — в
`wps-qa/cmp/<label>/report.html` (хранилище gitignored, в репозиторий не
входит).

Эталон — WPS Writer 12.1.0.28485, а не Word: если WPS сам ошибается, запись
получает статус `wps`.

## Статусы

| статус | значение |
|---|---|
| `open` | причина подтверждена, не исправлено |
| `triage` | симптом виден в метриках, причина не разобрана |
| `fixed` | исправлено; в записи — коммит и балл после исправления |
| `wps` | ошибка на стороне WPS, не наша |
| `metric` | артефакт измерения, а не рендера |

## Как воспроизвести

```
cargo +1.92.0 build --release -p strict-ooxml-cli
python xtool/wps-qa/wps_qa.py run --corpus <CORPUS> --label <label> --baseline <прежний label>
```

Чтобы получить картинку пары страниц (WPS | наш | наложение: красный — только
WPS, синий — только наш):

```
python -c "import sys; sys.path.insert(0,'xtool/wps-qa'); import metrics, numpy as np; from PIL import Image; \
S='wps-qa'; k='<CORPUS>/<doc>'; p,q=<стр. WPS - 1>,<наша стр. - 1>; \
img=metrics.diff_image(metrics.rasterize(f'{S}/refs/{k}.pdf',p,60), metrics.rasterize(f'{S}/ours/<label>/{k}.pdf',q,60)); \
Image.fromarray((img*255).astype(np.uint8)).save('diff.png')"
```

## Реестр

### WQ-001 · Маленький inline OLE-объект переносится на отдельную строку — `open`

- **Документ:** `CC0_DOCX_MATH/045_osf_Mathematical_Analysis_A_Continuous_Vacci`
  (стр. 6 у WPS ↔ стр. 7 у нас), и везде, где формула MathType стоит внутри
  строки.
- **Разметка:** обычный run с `<w:position w:val="-10"/>` и `<w:object
  w:dxaOrig="260" w:dyaOrig="300">`, внутри `<v:shape style="width:12.75pt;
  height:15pt">` + `<o:OLEObject ProgID="Equation.DSMT4">`.
- **WPS:** «Pelinearan pada titik tetap E₀ akan menghasilkan…» — одна строка,
  объект стоит в тексте.
- **Мы:** строка «Pelinearan pada titik tetap» растянута выравниванием по
  ширине, `E₀` стоит один на следующей строке, текст продолжается с третьей.
  То же для `R₀<1` (23,25 × 15 pt) в абзаце «Nilai eigen…».
- **Влияние:** каждый такой объект добавляет строку. В документе 191 объект
  MathType, значительная часть из них — inline, поэтому документ раздувается:
  11 страниц у WPS против 14 у нас. Слов на той же странице — 43%, F1
  переносов строк — 0,59.
- **Где искать:** раскладка inline-объектов `w:object` / VML `v:shape` в
  `strict-ooxml-render-svg/src/layout/` (перенос строки перед inline-объектом
  или отнесение его к блочным).

### WQ-002 · Свойства знака абзаца применяются к тексту абзаца — `open`

- **Документ:** `CC0_DOCX_MATH/045_osf_Mathematical_Analysis_A_Continuous_Vacci`,
  абзац «Nilai eigen yang kesemuanya adalah bilangan riil…» (стр. 6 у WPS).
- **Разметка:** `<w:pPr>…<w:rPr><w:b/><w:sz w:val="20"/></w:rPr></w:pPr>`, а у
  самих run-ов `rPr` только `<w:sz w:val="20"/>`, без `w:b`. Стиль
  `ListParagraph` жирности не задаёт.
- **WPS:** абзац набран обычным начертанием.
- **Мы:** весь абзац жирный.
- **Причина (гипотеза, проверить в коде):** `pPr/rPr` относится только к знаку
  конца абзаца (ECMA-376 §17.3.1.29), а у нас он, по-видимому, участвует в
  каскаде свойств run-ов.
- **Влияние:** жирный шрифт шире, поэтому строки переносятся иначе и абзац
  удлиняется.

- **Ещё документы:** 081 (подпись «Table S4…», см. WQ-028) и `CC0_DOCX_MATH/065_pmc_Integrated_computational_model_of_the_bi` — первый
  абзац введения «This supporting information file consists of four parts…»
  у нас жирный; `<w:b/>` только в `pPr/rPr`, у run-ов `rPr` пустой или `<w:i/>`
  (`wps-qa/065_p1.png`). Три документа — ошибка системная.

### WQ-003 · Текст MathType/WMF не попадает в текстовый слой PDF — `metric`

- **Документ:** тот же; затрагивает все документы с OLE-формулами.
- **Наблюдение:** recall текста 0,78. Из 944 «потерянных» слов почти все —
  символы формул (`1`, `0`, `a`, `b`, `m`, `g`, `r`…). WPS выводит текстовые
  записи WMF в PDF текстом, а мы рисуем превью картинкой. Глазами формулы на
  месте.
- **Решение:** не ошибка рендера. Метрика `text` занижает балл таких
  документов. То же для подписей осей внутри EMF-графиков (080: «abundance»,
  «parts per million», цифры шкал — у WPS текстом, у нас в растре). Возможная доработка инструмента — исключать из сравнения слова,
  которые у WPS лежат внутри области OLE-объекта.

### WQ-008 · Плавающая VML-рамка ставится от угла страницы, а не от колонки и абзаца — `open`

- **Документ:** `CC0_DOCX_MATH/045_osf_Mathematical_Analysis_A_Continuous_Vacci`,
  6 легенд графиков (`Gambar 4–7`). Картинка: WPS стр. 9 ↔ наши стр. 10–11.
- **Разметка:** `<w:pict><v:rect style="position:absolute;left:0;
  text-align:left;margin-left:28.8pt;margin-top:2.6pt;width:160.5pt;
  height:21.2pt">` с `<v:textbox>` в том же абзаце, что и inline-график.
  `mso-position-horizontal-relative` / `-vertical-relative` не заданы, поэтому
  по умолчанию VML отсчитывает по горизонтали от колонки, по вертикали — от
  абзаца-якоря.
- **WPS:** легенда «S(t) V(t) I(t) R(t)» лежит внутри графика, в его левом
  верхнем углу.
- **Мы:** рамка 214 × 28,27 px стоит в точке (38,4; 3,467) px = (28,8; 2,6) pt,
  то есть ровно `margin-left`/`margin-top` от угла **страницы**: над верхним
  полем, далеко от графика. Одинаково в SVG (`page-10.svg`, `<path d="M0 0
  H214 V28.267 H0 Z" transform="translate(38.4 3.467)">`) и в PDF.
- **Влияние:** все 6 легенд вне графиков, у верхнего края страницы.

### WQ-010 · `effectExtent` растягивает inline-картинку вместо отступа — `open`

- **Документ:** тот же, все 7 графиков (`<wp:inline>`, `<wp:effectExtent
  l="19050" r="9525">` = 1,5 / 0,75 pt).
- **WPS:** картинка размером ровно `wp:extent` (396,75 × 159,75 pt), сдвинута
  на `effectExtent.l`: x = 113,4 + 1,5 = 114,9 pt.
- **Мы:** картинка 399,0 × 159,8 pt с x = 113,4 pt, то есть
  `extent + effectExtent` по ширине. Растр сжат или растянут по горизонтали
  на 0,4–0,6%, левый край на 1,5–2,4 pt левее, чем у WPS. Одинаково в SVG и

- **Правильно:** `effectExtent` — это поля вокруг объекта под эффекты (тень,
  свечение), они участвуют в размере строки, а не в размере изображения
  (ECMA-376 §20.4.2.6).

### WQ-015 · Inline-картинка всегда занимает отдельную строку у левого края — `open`

- **Документ:** `CC0_DOCX_MATH/097_zenodo_Data_from_Study_on_the_optimization_of_t`:
  72 картинки `wp:inline`, по 2–4 в одном абзаце (4 × 102,1 pt = 408 pt;
  3 × 134 pt = 402 pt при ширине текста 415,3 pt), без пробелов между
  run-ами; большинство абзацев с `jc="center"`. Картинка:
  `wps-qa/097_all.png` (верхний ряд — WPS стр. 1–6, ниже — наши стр. 1–12).
- **WPS:** картинки стоят рядами по 3–4, ряд выровнен по центру; 9 страниц.
- **Мы:** каждая картинка на своей строке, столбиком у левого поля; 18 страниц.

- **Причина (по коду):** [`paragraph.rs:1327`](../strict-ooxml-render-svg/src/layout/paragraph.rs:1327)

  базовой линии — картинку нужно раскладывать так же.
- **Связь:** вероятно, та же причина у WQ-001 (OLE-превью MathType внутри

  маленькие (около 28 × 14 pt) внутри строк текста. Все растрируются, но

- **Ещё документ:** 083 — у WPS структура ChemDraw стоит в начале абзаца, и
  текст «: 4-Amino-2-hydroxybenzoic acid…» продолжается справа от неё по

- **Ещё документ:** `CC0_DOCX_MATH/065_pmc_Integrated_computational_model_of_the_bi`, заголовок «One-substrate one-product enzymatic
  reactions: S↔P» — `S↔P` (OLE MathType, `w:object` с

### WQ-016 · Текст, стоящий до плавающей таблицы, печатается поверх неё — `open`

- **Документ:** `CC0_DOCX_MATH/095_zenodo_OPTIMUM_PRETREATMENT_CONDITIONS_FOR_OBTA`,
  стр. 4, 6, 7. Картинки: `wps-qa/095_p4.png`, `095_p6.png`, `095_p7.png`
  (слева WPS, справа мы); общий вид — `wps-qa/095_all.png`.
- **Разметка:** 5 из 6 таблиц плавающие (`w:tblpPr`), четыре —
  `vertAnchor="page"` с абсолютной `tblpY` (2917, 3121, 10501, 5356 twips),
  одна — `vertAnchor="text"`; `leftFromText`/`rightFromText` = 180.
- **WPS:** текст обходит таблицу: на стр. 7 обтекает с обеих сторон
  («In last case, … | таблица | electropolishing by using E5…»), на
  стр. 4 и 6 абзацы уходят выше и ниже таблицы.
- **Мы:** абзацы печатаются прямо по ячейкам таблицы.
- **Причина (по коду, подтверждена порядком блоков):**
  [`place_floating_table`](../strict-ooxml-render-svg/src/layout/paginate.rs:670)
  ставит таблицу по абсолютной координате на текущую страницу и только
  **после этого** регистрирует зону обтекания в `wrap_exclusions`. Абзацы
  читают эти зоны в момент своей раскладки
  ([`paginate.rs:501`](../strict-ooxml-render-svg/src/layout/paginate.rs:501)),
  поэтому зону видят только абзацы, идущие **после** таблицы. Все
  наложившиеся абзацы стоят в документе раньше своей таблицы:
  «In first case» — блок 54, таблица 2 — блок 59; «In second case» — 93,
  таблица 4 — 105; «The role of perchloric», «In last case», «Aluminum
  reacts» — 133–136, таблица 6 — 142.
- **Что нужно:** таблицу, привязанную к странице, учитывать при раскладке
  всего текста этой страницы, включая абзацы до неё по порядку (как Word и
  WPS): например, перераскладывать страницу после регистрации зоны или

### WQ-030 · Формулы OMML: скобки-уголки, растянутый интеграл, короткий корень — `open`

- **Документ:** `CC0_DOCX_MATH/077_pmc_Development_validation_and_pilot_MRI_saf`,
  формулы (2), (3) на стр. 2 и (4) на стр. 3. Картинки: `wps-qa/077_nary.png`,
  `wps-qa/077_rad.png` (сверху WPS, снизу мы). Шрифт формул — Cambria Math
  (`m:mathPr`), `intLim="subSup"`, `naryLim="undOvr"`.

1. **Круглые скобки рисуются уголками.** `σ(r)`, `2ρ(r)`, `SAR(r)` у нас
   выглядят как `σ⟨r⟩`. Это и `m:d` с пустым `m:dPr` (по умолчанию `(`,
   парсер это делает правильно), и скобки, набранные **обычным текстом**
   внутри `m:r` (`<m:t>E(r)</m:t>` → у нас `E⟨r⟩`). Причина —
   [`shapes::delimiter`](../strict-ooxml-render-svg/src/math/shapes.rs:58):
   контур для `(` и `)` — две прямые, `M(1,0)→(0,15;0,5)`, `L(1,1)→(0,15;0,5)`,
   то есть по построению та же «галочка», что для `⟨` (U+27E8); `{`/`}`
   строятся кривыми, а `(`/`)` нет. И этот путь применяется даже к скобкам
   высотой в одну строку, где Word и WPS берут обычный глиф шрифта.
   Модули `|E(r)|` при этом тонкие и короткие, `²` отодвинут.
2. **Интеграл растягивается на всю высоту дроби.** `<m:naryPr><m:limLoc
   m:val="subSup"/></m:naryPr>`, `m:grow` нет. WPS рисует ∫ обычного
   «выключного» размера, предел `V_Head` — справа внизу. У нас ∫ —
   синтетический контур высотой с дробь, а предел уезжает далеко вниз, к
   концу этого контура. Причина —
   [`layout.rs:1518`](../strict-ooxml-render-svg/src/math/layout.rs:1518):
   рост включается при `nary.grow != Some(false)`, то есть и при
   **отсутствующем** `m:grow`. По ECMA-376 (§22.1.2.43) отсутствие `m:grow`
   означает «не растягивать» — сверить; Word по умолчанию интеграл не
   растягивает.
3. **Знак корня не доходит до низа подкоренного выражения.** `δ = √(2/ωμσ)`:
   у WPS знак охватывает всю дробь, у нас крючок кончается на черте дроби, а
   знаменатель `ωμσ` торчит ниже. Причина —
   [`layout_radical`](../strict-ooxml-render-svg/src/math/layout.rs:1320):
   `sign_height = -bar_y = radicand.height + gap` — без
   `radicand.size.depth`, а знаменатель лежит под базовой линией.
   **Ещё документ:** 074, формула (1) (`wps-qa/074_eq.png`, слева WPS,
   справа мы): оба `Σ` растянуты на всю высоту дроби (тот же рост n-арного
   оператора без `m:grow`), `(Mᵢ/10)` нарисовано как `⟨Mᵢ/10⟩` (п. 1),
   `=kLₒ` без пробелов вокруг `=`.
4. **Мелочи там же (не разбирались):** у нас `δ=` без пробелов вокруг `=` (у
   WPS с пробелами; `=` стоит в одном run с `δ`); `SARₕₑₐd` в тексте
   разорван («SAR h ead»), а в «(SAR_wb )» лишний пробел перед `)`.
