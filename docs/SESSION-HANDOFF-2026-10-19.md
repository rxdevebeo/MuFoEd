## 1. Что сделано

### 1.1 Строка таблицы выше страницы делится по строкам текста (`a64bb4e`)

`CC0_DOCX_1/033_Cornelis_de_Bruijn_The_Complete_Works` давал **24661** из
**26662** `off-page-text` всего корпуса (92%). Это таблица-примечание
(`w:tblW type="pct" w:w="278"`, `gridCol=440`) из узких однострочных абзацев;
каждая строка выше страницы уезжала вниз (стр. 736 доходила до `y ≈ −34 680`
при листе 1122 px).

**Причина:** `row_split_points` требовал **положительный зазор** между
чернильными полосами строк (`top > end + 0.01`). У однострочного текста
`ascent`/`descender` стыкуются ровно, точек разрыва было **ноль**, строка
считалась неделимой и не пагинировалась.

**Фикс:** стык двух полос — тоже граница (`row_fragment` относит текстовый
item по baseline, так что разрыв в стыке ничего не режет). Но вводить её
глобально нельзя — это ломало 5 документов (см. §1.3). Поэтому:

- `row_split_points(bands, height)` — прежнее поведение (только настоящие
  зазоры);
- `row_split_points_touching(bands, height)` — стык тоже граница;
- в `row_flows` `touching`-вариант выбирается **только когда
  `row.height > content_height`**, то есть строка физически не может
  поместиться на страницу и обязана делиться;
- в `Paginator::note_slice` — тот же `touching`-вариант, но только когда снота
  не влезает в бюджет (её всё равно надо делить).

Строка, которая **помещается** на страницу, по-прежнему переносится целиком и
делится только по настоящим зазорам — как Word/WPS.

**Регрессия:** `tests/tables.rs::a_single_row_taller_than_the_page_splits_across_pages`
(без фикса падает: 1 страница вместо ≥2). `tests/notes.rs::long_footnote_continues_on_next_page`
обновлён: снота выше страницы теперь **делится по строкам** между страницами,
проверяется, что текст сноты сохраняется целиком (`5 × "extra"`).

**Эффект на `033`:** страниц 1214 → **4813** (у WPS 5499), `off-page-text`
**24661 → 0** в самом документе, по корпусу **26662 → 1641** (−93.8%).

## 2. §3.2 `text-image` — исследовано и классифицировано, НЕ исправлено

Корпус: ours **1871** vs ref **1444** (+427). `RM0090` из плана на самом деле
**лучше** эталона (196 vs 240) — избыток в других документах. 46 документов с
положительным excess; топ:

```
+64 core-docx/Programming-Basics-CSharp-...      (ours 64, ref 0)
+51 CC0_DOCX_1/013_Vera_Veritas_website_blog_posts
+50 CC0_DOCX_MATH/023_dataverse_VISOR_SISMOMETRO
+31 core-docx/4. Complex-Conditions
+31 CC0_DOCX_MATH/031_osf_THE_EFFECT_OF_PORE_SIZE...
+29 CC0_DOCX_1/010_Electric_HypersonicAircraft
+27 core-docx/7. More-Complex-Loops
+26 CC0_DOCX_1/007_Valoracion_De_Aprendizaje...
```

### Классы причин

**A. Кроп `a:srcRect` — артефакт метрики.** Мы рисуем кроп, увеличивая битмап
и обрезая его рамкой; в PDF это видно буквально:

```
201 726.05 222 177.6 re  W  n            ← клип = видимая рамка 222×177.6 pt
314.4 0 0 232.5 149.8 700.3 cm  /Im_… Do  ← необрезанный бокс 314×232.5 pt
```

`pdfium.get_bounds()` возвращает **необрезанный** бокс (клип он не видит), WPS
хранит уже обрезанный битмап → его бокс = рамке. Визуально идентично, метрика
завышает. Документы: `013_Vera` (46/51 картинок с кропом, Σплощадь ×11.7),
`010_Electric` (8/8, ×9.3); слабее — везде, где кроп есть.

**B. `wrapNone` / `behindDoc` / `allowOverlap` — наложение задумано.**
Конвертированные/абсолютно-спозиционированные документы: `031` (13/13
`wrapNone`), `RM0090` (61–90 `wrapNone`, 16 `behindDoc`), серия
`core-docx/1..8` (по 3 `wrapNone` + 4–5 `wrapSquare` + десятки inline). WPS
такие картинки часто не выводит вовсе → ref = 0.

**C. Текст заходит в боксы `wrapSquare`/`wrapTight`/`wrapTopAndBottom` —
единственный кандидат на реальный дефект вёрстки.** Боксы картинок у нас
≈ эталона (Σплощадь ×1.00–1.16: `4.Complex` 1.05, `7.More-Complex` 1.00,
`3.Simple` 1.01, `5.Loops` 1.05), но `text-image` у нас 31/27/18, у WPS 0.
То есть дело не в размерах, а в том, что текст ложится под картинку.
Кандидаты: `wrapTopAndBottom` (`007` ×7), `wrapTight`+`wrapPolygon`
(`013` ×38, `023` ×5, `005`, `082`).

**D. Картинки колонтитула** поверх первых строк тела (`007`: 3 картинки в
`header1.xml`).

## 3. План

### 3.1 Обтекание (C) — наибольший исправимый вклад
Минимальные репро: `core-docx/4. Complex-Conditions` стр. 2 (2 картинки,
`text-image` 31, ref 0) или `007` стр. 15. Проверить `page_exclusion` в
`layout/floating.rs` для `wrapSquare`/`wrapTopAndBottom`/`wrapTight`: текст
обязан обходить бокс + `dist*` + `effectExtent`. Учесть, что часть наложений —
ожидаемые `wrapNone`.

### 3.2 Кроп (A) — метрика или рендер
Либо научить `overlap.py` учитывать клип (`re W n` перед `Do`) — метрика
станет честнее без правки рендера; либо пред-кропать битмап, как WPS (тогда
совпадут и боксы). Первое безопаснее и проверяемо.

### 3.3 B/D — задокументировать
`031`, `RM0090`, `core-docx/1..8`, колонтитулы `007` — пометить в
`WPS-QA-DISCREPANCIES.md` как «наложение задумано / WPS не выводит объект»,
чтобы не гонять их в следующих сессиях.

### 3.4 Остальное (из прошлой передачи)
- `text-over-lines` 13121 vs 6465, `text-text` 9724 vs 3435 — в основном те же
  артефакты, что в §1.10 прошлой передачи (вязь, водяные знаки, дубли-рамки);
  `PROBE_027` (+2525) — пробный корпус.
- `text-image-bg` 342 vs 158; `off-page-image` 323 vs 160.
- `image-image` ours 99 vs ref 943 — у WPS **больше**: артефакт WPS, не цель.
- CCX (23 файла) — HTML под `.docx` (`<!DOCTYPE html>`), ридер падает
  `invalid ZIP`.
- `core-samples/sample-docx-200kb` — отказ на необъявленном префиксе `wp14`.
- Content-loss: глифы-квадраты, раздувание страниц — лечится шрифтовыми паками
  (`fonts install <pack>`).
