# Reference renders (WPS Office)

Per-document reference PNGs used by the SSIM gate
(`strict-ooxml-render-svg/tests/ssim.rs`,
`STAGE-4-RENDER-FIDELITY.md` S4F.4/S4F.5).

## Layout

```
refs/<document>/page_N.png   # N = 1-based page
```

`<document>.docx` is the matching fixture in `tests/strict/`.

## Generator (pinned)

| Item | Value |
|---|---|
| Engine | WPS Office `12.1.0.28485` (`kwpsconvert.exe`) |
| Command | `kwpsconvert.exe word2photo --input <docx> --output <dir>` |
| Output | `<dir>/<stem>/page_N.png` |
| DPI | 96 DPI |
| Page sizes | `strict-text` 816×1056 (Letter); `strict-text-grid` 816×1056; `strict-profile` 727×1055 (page size from its `w:pgSz`, `545.30pt`×`791.90pt`); `05`/`06`/`07`/`09`/`10` 816×1056 |

Background: this WPS build was verified to **read Strict** documents and emit
one PNG per page. References are generated **once** on this pinned version and
committed; WPS is **not** required in CI. Regenerating on a different version is
not reproducible and is out of scope.

## Documents

Every document in `SSIM_DOCS` is graded in three states, not two. `SSIM`
below `0.95` is a regression and fails. `SSIM` in `[0.95, 0.96)` is *amber*:
it passes only because the document is written down in `SSIM_AMBER`, so a new
fixture cannot join the gate just below the line without being registered on
purpose. The register is checked in both directions — a stale entry fails the
gate too — so it cannot quietly become a graveyard. The margin is 0.01
because several documents clear 0.95 by three thousandths, and the gate runs
on three operating systems; whether that number is a property of the layout or
of one rasterizer build is not something the score can tell you.

All of it — the threshold, the margin, the content classes, which document
belongs to which class, and the structural bounds per class — lives in
[`coverage/render-gates.toml`](../../../../coverage/render-gates.toml) with its
justification beside it, and `tests/ssim.rs` reads it. Two guards keep the table
honest: every reference directory must declare a class, and every class must
name documents that exist. The rationale for each bound is in the file, next to
the bound, so loosening one is a reviewable diff in the place that also says
what loosening it costs.

The structural invariant (`tests/ssim.rs`) additionally requires similar ink
coverage, row/column ink-profile correlations (≥ 0.9 / ≥ 0.85), profile
alignment and ink-centroid drift within 2 / 2.5 px on **both** axes, plus an
**ink-extent** bound: the first and last substantial ink row (≥ 6 ink pixels)
must sit within 2 px of the reference. The extent check is what a block that
is a whole line too tall cannot hide from — the centroid averages over the
page and the profile correlation is computed *after* the best alignment, so
neither of them sees it. It rejects a blank page or a ≥ 3 px shift on either
axis, which SSIM alone tolerates (horizontal shifts up to ~10 px).

The alignment search window is derived from the bound
(`max_shift_px + ALIGNMENT_SEARCH_MARGIN_PX`), never a fixed constant: a search
window equal to the bound cannot report a shift outside it, which would make
the check unfailable. `alignment_search_range_is_wider_than_every_bound` pins
that invariant.

`strict-stage5c`, `06`, `07` and `10` currently exceed the 2 px extent bound
(17 / 10 / 16 / 3 px). Their drift is pinned per page by `EXTENT_RATCHET` in
`tests/ssim.rs`, which fails if any page drifts *further* and fails if a page
gets better without the pinned value being lowered — the ratchet is how the
known block-geometry defect is tracked down, not a tolerance.

The extent counts ink cumulatively from each page edge rather than requiring a
threshold within a single row. A per-row threshold cannot see a vertical rule:
a 3 px page border contributes ~3 pixels to each of the ~1000 rows it runs
down, so a per-row filter drops it. That is not hypothetical — `strict-stage5b`
shipped a page border whose vertical rules ran the full page height, past the
horizontal ones, with every structural bound satisfied (the extent check
reported ±1 px). The border is now drawn as the closed box ISO/IEC 29500-1
§17.6.2 specifies, and the cumulative extent reports the old rendering as
−23/+23 px.

## Stage-5 fixture

`tests/strict/strict-stage5.docx` is a synthetic Strict fixture covering the
Stage-5 subsystems (headers/footers, footnotes/endnotes, computed fields, a
complex table with gridSpan/vMerge/tblHeader, a theme and multi-level
numbering). It is generated deterministically by
`cargo run -p xtool -- gen-docx --stage5 --out <path>` (S5.12) using standard
ISO/IEC 29500 content types (`STAGE-5-REWORK-1` B5-2).

It is validated structurally — parse model, Feature Report, two-page SVG render,
and an independent XML oracle (`zip` + `roxmltree`,
`strict-ooxml-wml/tests/stage5_fixture_oracle.rs`) — and by WPS pixel references
(`refs/strict-stage5/`, pinning `12.1.0.28485`): worst SSIM = 0.9795 with the
2-page invariant and the **structural invariant** (ink coverage/blank, alignment
shift ≤ 2 px, ink centroid ≤ 3 px) using relaxed profile-correlation thresholds
(`STAGE5_LIMITS` in `tests/ssim.rs`; `STAGE-5-REWORK-1` R5-1): the sparse mixed
table/footnote content keeps the row/column correlations below the text-only
thresholds, but a blank render is still rejected.


## Stage-5B fixture

`tests/strict/strict-stage5b.docx` is a synthetic Strict fixture covering the
Stage-5B floating-drawing subsystem (anchored shape, group of two shapes, text
box, anchored picture, page borders). It is generated deterministically by
`cargo run -p xtool -- gen-docx --stage5b --out <path>`.

`WordprocessingShape`/`WordprocessingGroup` are **Microsoft extensions** (not ISO
Strict schemas); the fixture therefore declares them in
`http://schemas.microsoft.com/office/word/2010/wordprocessingShape` /
`.../wordprocessingGroup`, exactly as real Word Strict documents do
(`strict-profile.docx`). The core stays ISO (`w`/`wp`/`a`/`pic`) and
`w:txbxContent` remains in the ISO WML namespace. With the ISO-looking
`purl.oclc.org/.../wordprocessingShape` URI WPS renders only the page border,
which is why the earlier Stage-5B report wrongly called the oracle inapplicable
(`STAGE-5B-REWORK-1` 5B-1).

It is validated by an independent XML oracle (`zip` + `roxmltree`,
`strict-ooxml-wml/tests/stage5b_fixture_oracle.rs`), the corpus test
(`strict-ooxml/tests/stage5b_corpus.rs`) and by the WPS pixel reference
(`refs/strict-stage5b/page_1.png`, pinning `12.1.0.28485`): worst SSIM = 0.9640
with the structural invariant (ink coverage/blank, alignment shift ≤ 2 px, ink
centroid ≤ 8 px because the large solid fills make the WPS fill-edge
antialiasing shift the centroid while profile alignment is exact) using relaxed
profile-correlation thresholds (`STAGE5B_LIMITS` in `tests/ssim.rs`; a blank or
page-border-only render is still rejected — `STAGE-5B-REWORK-1` 5B-2).

## Stage-5C fixture

`tests/strict/strict-stage5c.docx` is a synthetic Strict fixture covering every
OMML construct of `STAGE-5C-TASK.md` §3.1 — `m:oMath`, `m:oMathPara` + `m:jc`,
runs and `m:rPr`/`m:argPr`, `m:f`, `m:rad`, `m:sSup`, `m:sSub`, `m:sSubSup`,
`m:sPre`, `m:nary`, `m:d`, `m:func`, `m:limLow`, `m:limUpp`, `m:m`, `m:eqArr`,
`m:acc`, `m:bar`, `m:groupChr`, `m:box`, `m:borderBox`, `m:phant` and the
properties `m:maxDist`, `m:objDist`, `m:baseJc`, `m:defJc`, `m:lit`,
`m:smallFrac`, `m:type`, `m:pos`, `m:vertJc` — each once inline and once as a
display formula. It is generated deterministically by
`cargo run -p xtool -- gen-docx --stage5c --out <path>`.

OMML is a native part of ISO/IEC 29500-1, so the fixture uses only the Strict
math namespace `http://purl.oclc.org/ooxml/officeDocument/math` and WPS renders
it with its own math engine.

It is validated by an independent XML oracle (`zip` + `roxmltree`,
`strict-ooxml-wml/tests/stage5c_fixture_oracle.rs`), which cross-checks the
constructs, the namespaces and the concatenated `m:t` text against our model —
and, since `STAGE-5C-REWORK-1`, the same oracle for the three real repro
packages `05`/`06`/`10` — plus the render tests
(`strict-ooxml-render-svg/tests/math.rs`) and the end-to-end corpus test
(`strict-ooxml/tests/stage5c_corpus.rs`).

The WPS pixel reference is **gated** on both pages: worst SSIM **0.9533**
against the 0.95 criterion of `STAGE-5C-TASK.md` §11.2, with `STAGE5C_LIMITS`
(`tests/ssim.rs`) and the 2-page invariant. The `PENDING_DOCS` /
`PENDING_PAGE_SKIP` exemptions that the previous acceptance carried are gone.

### The producer-defect claim of the previous acceptance, re-examined (C2)

The previous acceptance excluded page 1 (index 1) with the claim that "WPS
`12.1.0.28485` lays consecutive `m:oMathPara` on top of each other". **That
claim was wrong, and it was our defect.** WPS page 2 of `strict-stage5c` is
three *separate* display blocks at y 115–141, 144–187 and 190–231, stacked
normally; the page rendered correctly. The cause of the 15-band / 467 px
render was ours, in two parts: an `m:eqArr` row spacing read as points instead
of twips, and a display-formula paragraph that emitted an empty line above and
below its own block. Both are fixed, the page is compared like any other, and
no minimal reproduction of a "WPS defect" exists because there was none.
