# Общий runtime моделей MuFoEd

## Цель и границы

Один host-owned `mufoed-model-runtime` для текста, vision/OCR, генерации,
сегментации, удаления фона и апскейла. При встраивании редактора изображений
MuFoEd передаёт клон своего `Runtime` в `ImageEditor::with_runtime`.
Менеджер не зависит от egui, Plakat, Candle, PyTorch, Ollama или StrictLib.
Изменения адаптеров StrictLib не требуются: точки интеграции находятся в MuFoEd.

`Runtime::global()` — общий экземпляр внутри одного процесса. Отдельно запущенные
MuFoEd и Image Studio пока имеют независимые менеджеры. Ollama — отдельный сервер;
его память нельзя считать освобождённой только по завершению HTTP-запроса.
Чужие приложения и запросы других клиентов Ollama менеджеру не подчиняются.

### R01: исходный контракт этапа (история; дополнен R03–R05)

- `Task`: владелец, backend/model, устройство, оценка пиков RAM/VRAM в байтах.
  Метка `model` диагностическая, использовать её как ключ совместимости кэша нельзя.
- `Policy`: доступные лимиты после вычета резерва host-приложения, очередь до 64
  ожидающих задач по умолчанию. CPU и GPU inference пока выполняются строго по одной.
- `enqueue` ничего не загружает. `Ticket::try_start` не блокирует UI.
  `Ticket::wait` предназначен для worker; проверяет отмену и deadline.
- `Lease` принадлежит исполнителю, а не UI: subprocess освобождает его после reap,
  встроенный backend — после выхода из inference и уничтожения локальных моделей.
  Отмена ожидающего ticket удаляет только этот ticket, не соседние задачи.
- Plakat native/CLI и Python inference принимают `start_with_runtime`; старые
  `start` используют process-global runtime. Замена документа сохраняет host runtime.
  Python downloads не занимают inference-очередь; их текущая проверка ONNX идёт на CPU.
- Статус редактора показывает текущего владельца и длину общей очереди.
- Лимиты по умолчанию **не настроены**. Если host задаёт лимит, неизвестная оценка
  отклоняется (`UnknownEstimate`), превышение — `OverBudget`, до запуска backend.
  Текущие графические адаптеры ещё не имеют калиброванных оценок. R01 не измеряет
  реальную свободную VRAM, не выгружает idle-кэш и не предотвращает любой OOM.
- Встроенный Plakat дополнительно сохраняет собственный non-reentrant guard.
  Его активная отмена пока отбрасывает результат; разрешение остаётся у worker.

### R02: исходные точки интеграции (история; lifecycle дополнен R04)

Реализовано в `model-runtime/src/ollama.rs` и `mufoed/src/model_runtime.rs`.
Все перечисленные ниже production-пути используют общий process-global runtime.

Проверены исходники worktree; основной граф не покрывает новый image-editor.

- `mufoed/src/ai.rs::chat_with`: AI-команды и чтение текста с изображения.
- `mufoed/src/chat.rs::post`, `Remote::complete`: чат с инструментами.
- `mufoed/src/formats.rs::vision`: OCR при импорте.
- `mufoed/src/raster.rs` и `worker.rs::recognize_object`: OCR/формулы/объекты.
- `context_window` и выбор модели не должны выполнять скрытую загрузку вне допуска;
  metadata/list/download не занимают GPU-lease, но проверяются на побочные загрузки.

Нужен общий Ollama-адаптер на стороне MuFoEd, включая wrapper над имеющимся
`TextRecovery`, без изменения библиотечного крейта. Владение задаётся endpoint +
model + instance/job. Удалённый endpoint имеет отдельный resource domain: его VRAM
не прибавляется к локальной, и локальная очередь не должна ждать удалённую GPU.

Стартовая политика для локальных моделей — управляемый `keep_alive` и явная
выгрузка только собственных idle-моделей. Поддержка `keep_alive: 0` описана в
[Ollama Chat API](https://docs.ollama.com/api/chat).
После timeout/обрыва связи нельзя просто вернуть lease: сервер мог продолжить
инференс. Состояние `releasing/unknown` удерживает конфликтующий допуск до проверки
сервера или явного восстановления. HTTP adapter должен вернуть подтверждённый
terminal outcome, а не лишь `Result` содержимого ответа.

Текущая политика R02: перед inference `/api/tags` даёт fingerprint, `/api/ps`
проверяет, что выбранная модель/тот же digest не были загружены сторонним клиентом.
Такая модель не принимается во владение и не выгружается; запрос получает отказ
до compute. После собственной операции посылается unload только выбранной модели:
нужны `done: true`, `done_reason: unload` и отсутствие модели/digest в `/api/ps`.
Отсутствие в `/api/ps` само по себе не завершает неизвестную загрузку.
Если подтверждение не получено, registry и recovery worker продолжают удерживать
lease; восстановление повторяется с интервалом 2 с, HTTP ограничен 10 с.

Обычная ошибка результата сохраняется после успешного release; при ошибке release
сообщаются обе причины. Panic передаёт cleanup в recovery через RAII. Текст/чат
передают флаг отмены в очередь; уже выполняющийся HTTP-запрос не прерывается —
результат отменённой задачи отбрасывается после release. У существующих import/OCR
API отдельного UI-флага отмены запроса нет: они ждут в очереди до лимита 900 с.
Callbacks остаются синхронными и не должны запускать detached inference.

Это режим освобождения после каждого запроса, включая абзацы/страницы. Warm reuse
и удержание совместимых весов между запросами появятся в R04. Чужие клиенты Ollama
могут загрузить ту же модель после preflight: API не предоставляет эксклюзивную
серверную lease. Для такой конкуренции абсолютная гарантия владения невозможна;
конкурирующие приложения/OS-процессы требуют выделенного endpoint или broker.
LAN/нелупбэк-адрес считается remote; для локального Ollama использовать loopback.

### UI01: ручные инструменты и менеджер слоёв

Реализованный продуктовый этап после R02, перед продолжением R03–R05. Проверки и границы: [UI01-VALIDATION.md](../image-editor/UI01-VALIDATION.md).

Контракт этапа:

- Узкая палитра рядом с холстом, параметры активного инструмента сверху,
  слои/цвет в правом доке; вкладки ИИ «Создание / Редактирование / Апскейл»
  сохраняются отдельной панелью. Отступы и размеры контролов согласованы,
  палитра MuFoEd с синим акцентом, без жёлто-зелёного.
- Группы выделения/перемещения, кисти/ластика/маски, заливки/градиента,
  пипетки, кадрирования и фигур. Реализовать недостающие операции в image-editor,
  поддержать radius/hardness/opacity и цвет там, где это применимо. Иконки,
  подсказки, горячие клавиши и различимое активное состояние.
- Список слоёв с миниатюрами, именем, выделением активного слоя, видимостью,
  блокировкой редактирования, opacity и drag-and-drop порядка. Добавление,
  дублирование, переименование, удаление и объединение в явных действиях.
- Не показывать фиктивные работающие инструменты или неподдержанные blend modes.
  Маска визуально отличается от изображения; ясно, куда применяется операция.
- Приёмка: вся палитра и действия слоёв проверены мышью/клавиатурой, операции
  отменяются/повторяются, сохранение/открытие не теряет порядок/свойства/пиксели;
  UI проверен на узком и обычном окне с настоящим многослойным изображением.

### R03: бюджет и решения при нехватке

1. Получить физическую/свободную память выбранного устройства и RAM с timestamp.
   Не использовать номер GPU по порядку как постоянную идентичность; хранить UUID.
2. Вычесть настраиваемый резерв для MuFoEd, renderer и ОС. Начальный ориентир VRAM
   — max(1 GiB, 10% физической памяти), уточнить замерами; это реализованный default R03.
3. Оценить пик: резидентные веса + активации + временные копии + workspace backend.
   Для LLM учитывать KV-cache/контекст; для изображений — размер, dtype, batch,
   LoRA, VAE и tile. Размер файла модели не равен требуемой VRAM.
4. Освободить собственные idle-ресурсы: сначала GPU → CPU при допустимой RAM,
   затем полная выгрузка по LRU. Активные leases и чужие процессы не трогать.
5. Дождаться подтверждения адаптера, измерить память заново. Если пик не помещается,
   вернуть структурированный отказ с нужной/доступной памятью и вариантами действий.
   Не менять разрешение, модель, dtype или устройство без выбранной пользователем политики.
6. Если телеметрия недоступна/устарела — явно сообщить unknown; не показывать
   выдуманную свободную память. Для строгого режима отказать до allocation.

### R04: размещение компонентов и кэш

Ключ совместимости: fingerprint весов/revision, backend/version, device UUID,
dtype, семейство, конфигурация tokenizer/text encoders, VAE, LoRA + scale и
conditioning. Размер изображения влияет на рабочий бюджет, но не обязательно
требует повторной загрузки одних весов. Для SAM отдельно ключ изображения и points;
изменение points не должно заставлять пересчитывать совместимые image embeddings.

Состояния: unloaded → loading → resident CPU/GPU → active → idle → offloading/
unloading → unloaded; ошибка во время перехода не публикует запись как ready.
Адаптер предоставляет prepare/load, run, offload, unload, measured footprint и
подтверждение завершения. Вызовы адаптеров выполняются вне блокировки менеджера.

Последовательность SDXL: encode prompt → убрать text encoders с GPU → denoise →
убрать denoiser → VAE decode. Img2img/inpaint учитывают также VAE encode перед
denoise; обе половины не должны незаметно держать все компоненты на GPU.
Staged adapter использует публичные компоненты Plakat за pinned revision, отдельно
создаёт CLIP/UNet/VAE на устройстве и освобождает их между стадиями; CPU-веса
сохраняются в общем кэше. Fork Plakat не потребовался. Не менять StrictLib. Для смеси апскейлеров сохранить
последовательное выполнение с промежуточным изображением в RAM.

### R05: ошибки и итоговая приёмка

- OOM: максимум один повтор после очистки временных ресурсов и idle eviction;
  повторять только транзакционную операцию с тем же seed/параметрами. Снижение tile
  разрешено лишь для backend, где подтверждена допустимая семантика результата.
- Очередь не зависает после отмены, ошибки загрузки, panic, смерти subprocess,
  отказа Ollama и закрытия окна. Не отдавать lease раньше окончания compute/unload.
- UI показывает ожидание, loading, inference, offload, ready, failed; отдельно
  оценки, реальные измерения и unknown. Команда освобождения отменяет idle residency,
  но не прерывает активную чужую операцию.
- Сценарий: LLM с большим контекстом → SDXL encode/denoise/VAE → SAM → смесь
  UltraSharp/AuraSR → LLM, затем те же переходы с отменой и нехваткой VRAM.
- Проверить warm reuse без загрузки весов, корректную смену LoRA/VAE/модели,
  освобождение памяти по реальным измерениям и неизменность документа/Undo.

## Реализованный итог R03–R05

`Runtime::global()` теперь использует `SystemTelemetry` и строгий managed admission.
`Runtime::new` сохраняет режим одного координатора без физической телеметрии для
тестов/специальных хостов. Для production host может задать `Runtime::managed`.

- R03: RAM из ОС, VRAM из NVIDIA по UUID, возраст замера до 5 с; резерв RAM
  max(2 GiB, 5%), VRAM max(1 GiB, 10%). Очередь и preflight работают вне UI.
  Перед выделением — оценка полного пика, вычет только точного собственного
  совместимого кэша, LRU offload/unload и новый замер. После eviction вычет
  пересчитывается. Неизвестные/устаревшие данные в strict mode дают отказ.
  Фиксированные лимиты host проверяются и для отложенного плана native backend.
- R04: CPU-кэш весов Plakat, отдельные device-модели CLIP/UNet/VAE по стадиям,
  persistent Python workers для ONNX/SAM/апскейлеров, SAM image embeddings.
  Ollama удерживает собственную совместимую модель с фактическим context size;
  чужая residency не принимается во владение. Ключи включают содержимое весов,
  revision/version, dtype, device UUID и соответствующие LoRA/scale/config.
  Цель известного idle CPU-кэша — 12 GiB; активные pinned-ресурсы не вытесняются.
- R05: максимум один OOM-retry с теми же параметрами после подтверждённой очистки;
  ошибка unload переводит manager в quarantine. Отмена native проверяется между
  компонентами и шагами, Python — kill/reap, Ollama — удержание lease до подтверждения.
  Закрытие host прекращает новый admission и ждёт свои локальные/remote domains.
  Окно «Память моделей» показывает замеры, оценки, unknown, кэш и реальные стадии;
  обновление и ручное освобождение выполняются через очередь.

[Воспроизводимая приёмка, команды и ограничения](R345_VALIDATION.md).
Отчёт отделяет аппаратные проверки от injected OOM/ошибок и неподтверждённых вариантов.

## Оставшиеся границы

Менеджер общий внутри host-процесса; межпроцессный broker не реализован.
Физический бюджет не защищает от одновременных выделений чужих процессов.
Без однозначного NVIDIA GPU strict auto отказывает; другие GPU backends и
другие семейства checkpoint требуют отдельной аппаратной приёмки.
У Ollama нет эксклюзивной server lease, поэтому чужой клиент может вмешаться
между проверкой и запросом; для такой конкуренции нужен выделенный endpoint/broker.
Native сохраняет CPU-веса, но заново создаёт device-модели по стадиям;
GPU pipeline целиком между запросами не удерживается. Диагностический CLI
одноразовый: без resident reuse и автоматического retry.
