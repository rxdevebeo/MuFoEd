# Этап 8. Конвертация PDF ↔ Strict

**Заказ:** ZAKAZ-STAGE-8  
**Основание:** `base_target.md` §3.3 («Рендеринг в PNG/PDF» — опционально после
MVP), §3.2 («Сохранение в Strict» — **снимается этим заказом**), `TZ-STRICT-OOXML-
RUST.md` §15 (этапы 0–6 закрыты, этап 7 — релиз)  
**Дата:** 2026-09-30

> Один заказ — четыре фазы (8A…8D) с общей приёмкой. Каждая фаза сдаётся
> отдельно, но ни одна не считается закрытой без `SC-*` ниже.

---

## 0. Постановка задачи

Нужны **оба** направления:

```
Strict .docx  ──(8A+8B)──▶  PDF            «прямая»
PDF           ──(8A+8C)──▶  Strict .docx    «обратная»
```

**Прямая** конвертация низкого риска: движок вёрстки уже есть, нужен второй
backend поверх него.

**Обратная** — принципиально новая territory, и вот почему. В проекте **нет
писателя `.docx` вообще**: `TZ` §3.2 и `STAGE-6-TASK.md` §6 держат сохранение
за пределами MVP, а `xtool/src/main.rs:1294` (`fn zip`) собирает только
фикстурные пакеты из строк. Поэтому обратная конвертация упирается не в PDF, а
в **сериализацию в Strict** — и это отдельный продукт, полезный сам по себе
(и для «Transitional → Strict на диск», и для round-trip-проверок).

Порядок поэтому такой: сначала 8A (писатель), потом 8B (PDF-вывод), потом 8C
(чтение PDF), потом 8D (OCR/графика). Обратное направление без 8A невозможно.

### 0.1 Ответ на исходный вопрос «это уже делали»

Нет. Проверено по `git log` и по корпусу документов:

| Проверено | Где | Результат |
|---|---|---|
| Рендеринг в PDF/PNG | `base_target.md:95`, `STAGE-4-TASK.md:50` | отложено, сделали только SVG |
| Писатель `.docx` | `TZ-STRICT-OOXML-RUST.md:147` | вне scope, не начат |
| Упоминания `pdf` в коде | `STAGE-4-RENDER-FIDELITY.md:128` | только `kwpsconvert word2pdf` для эталонов SSIM |
| Крейты PDF/записи | `Cargo.toml` | отсутствуют |

Единственный работающий PDF-конвейер сегодня — внешний WPS, и то как
**генератор эталонов**, а не как часть библиотеки.

### 1.1 Долг, который вскрывает 8B

`layout` в `render-svg` — `pub(crate)`, и крейт назван `…-render-svg`, хотя
вёрстка к SVG не относится. Решение: **открыть `layout` публично** (≈10 строк
изменений) и зафиксировать в ADR-0008, что переименование крейта в
`strict-ooxml-render` выполняется **до публикации на crates.io** (этап 7) —
сейчас это чисто косметический долг, а не блокер.

### 2.1 MSRV

`rust-version = "1.75"` в workspace **не выдерживается** ни одним из кандидатов
(minimum по `lopdf` — 1.88). CI MSRV не гейтит (`dtolnay/rust-toolchain@stable`),
локально 1.91.x, так что подъём безопасен: **поднимаем MSRV крейта до 1.85**
(минимум `subsetter`/`ureq`; `lopdf` 0.45 требует 1.88 — фиксируется в ADR как
причина выбора `lopdf` 0.45, а не 0.37). Фича `raster` (`hayro`) требует 1.92 и
**не входит** в MSRV-гейт: она не входит в дефолтные сборки.

### 2.2 Транспортная честность (детерминизм)

`pdf-writer` пишет объектные номера по порядку вызовов, поэтому вывод
детерминирован, если порядок обхода DOM детерминирован (он такой: §11 ADR-0004,
интернирование). В PDF **не пишется** дата создания: берём
`/CreationDate` из `RenderOptions` (по умолчанию — фиксированный epoch) либо
не пишем вовсе. Критерий SC-1 проверяет побайтовую воспроизводимость.

## 3. Фаза 8A — `strict-ooxml-write`: сериализация в Strict

Первая и обязательная: без неё обратное направление не существует.

**Вход:** `wml::model::Document` (+ байты media-частей). **Выход:** байты `.docx`.

| # | Требование |
|---|---|
| W1 | Сериализация DOM → `word/document.xml` в **Strict**-неймспейсах (`purl.oclc.org/ooxml/...`), без Transitional-сигналов |
| W2 | `styles.xml`, `numbering.xml`, `settings.xml`, `theme1.xml`, `footnotes.xml`, `endnotes.xml`, колонтитулы, `fontTable.xml` — из соответствующих таблиц DOM |
| W3 | `document.xml.rels`, `_rels/.rels`, `[Content_Types].xml` (Override для каждой части, `Default` для `rels`/`xml`/медиа) |
| W4 | Media-части (`image1.png` …) + их `Content_Types` по расширению; DrawingML (`wp:inline`/`wp:anchor`, `a:blip r:embed`, `wps:wsp`, `a:custGeom`, OMML) |
| W5 | Запись ZIP (deflate, детерминированные mtime/порядок записей) — переносится из `xtool` в `core::opc::zip::write` |
| W6 | Никаких `unwrap`/паник; лимиты на размер и глубину |
| W7 | **Pass-through несмоделированных частей** (chart, diagram, OLE, custom XML): копировать из исходного пакета как есть, вместе с их `.rels` и content types |

**Явно не входит:** редактирование существующего документа (dif-патчи),
экспорт в Transitional, сохранение неразобранных частей «как есть».

### 3.1 Состояние 8A на 2026-09-30

W1–W6 **закрыты**: крейт `strict-ooxml-write`, 17 юнит-тестов + 12 интеграционных,
`strict-ooxml write` в CLI. Проверено: SC-1 (побайтовая воспроизводимость), SC-3
(написанный пакет — **неподвижная точка** повторной записи, все части
well-formed по `roxmltree`, Strict по независимой проверке namespace'ов), SC-4
(**WPS 12.1.0.28485 открывает написанный `.docx`** и конвертирует его в PDF),
SC-10 (инвариант «потеряно ⇒ записано в отчёт»).

**W7 не начат и это единственный открытый пункт фазы.** Измеренно на
`strict-profile`: оригинал — 2 страницы, написанный пакет — 1; диаграмма и
график потеряны, текстовое поле внутри диаграммы сохранилось. Потеря фиксируется
в отчёте (`W1.unserializable`), CLI возвращает `1`. Waiver `8A-CHART` в
`docs/waivers.toml`. До W7 команда `write` пригодна для нормализации
Transitional → Strict «на диск» и для round-trip-проверок, но не для документов с
графиками.

## 4. Фаза 8B — `strict-ooxml-render-pdf`: Strict → PDF

**Вход:** `Document` + media. **Выход:** один `.pdf`.

| # | Требование |
|---|---|
| P1 | Переиспользовать `layout::paginate::layout_document`: те же страницы, та же пагинация, тот же набор `Item` |
| P2 | Backend `Item::Text` → настоящий текстовой оператор `Tj` с встроенным шрифтом, **не** картинка: текст выделяется, ищется, копируется |
| P3 | Сабсеттинг бандловых OFL-шрифтов (`subsetter`), встраивание как `CIDFontType2` / `Identity-H`, `W`-массив из метрик, `ToUnicode` CMap |
| P4 | `Item::Image`: JPEG (`DCTDecode`) — байты прозрачно; PNG — декод через `png` в RGB + `SMask` для альфы |
| P5 | Геометрия страницы из `sectPr` (twips → pt, `twips / 20`), `MediaBox`, `Rotate` для альбомной ориентации |
| P6 | Детерминированный вывод; без даты; лимиты на число страниц/шрифтов/объектов |
| P7 | Ссылки-аннотации не генерируются; `MAX_PAGES` наследуется из движка вёрстки |

**Почему не `svg2pdf`:** SVG — потерянный промежуточный слой (текст растрируется
или требует ручной подстановки шрифтов), плюс тянет `usvg`-растеризатор в граф.
Наш layout уже отдаёт абстрактные `Item` — второй backend пишется за день.

### 4.1 Состояние 8B на 2026-09-30

**P1–P7 закрыты.** Крейт `strict-ooxml-render-pdf`, 28 юнит-тестов + 8 интеграционных,
`strict-ooxml to-pdf` в CLI.

- Движок вёрстки открыт наружу (`render-svg::place_pages`, `Item`, `PlacedPage`),
  PDF — второй backend над **той же** раскладкой, поэтому расхождение по числу
  страниц невозможно по построению (SC-6, проверено на 4 документах).
- Текст — настоящий: 16 бандловых лиц сабсеттятся (`subsetter`, с инстанцированием
  переменного Arimo) и встраиваются как `Type0`/`CIDFontType2` + `Identity-H` +
  `ToUnicode`. **Проверено независимым ридером `pypdf`**: текст извлекается как
  текст, в правильном порядке (SC-7).
- Потоки сжимаются вручную: `pdf-writer` записывает `/Filter`, но не сжимает —
  поток, заявляющий `FlateDecode` с несжатыми байтами нечитаем.
- Изображения: JPEG проходит прозрачно (`DCTDecode`), PNG декодируется в сэмплы +
  `/SMask` для альфы; GIF/BMP/TIFF/EMF — запись потерь.
- Воспроизводимость побайтовая (SC-1): порядок выдачи object-id — часть контракта.

**Ограничения, зафиксированные здесь:** кривые Безье сохраняются как кривые
(`c`); путь приходит в backend строкой SVG-path-данных и разбирается обратно
(осознанный размен, ADR-0008); картинки без media-источника становятся
placeholder с записью в отчёт; шрифт без глифа — символ не рисуется и пишется в отчёт.

**SSIM-гейт фазы (SC-6, полная форма) не включается:** общий гейт
`render-svg/tests/ssim.rs` сейчас красный по незавершённой правке соседней сессии
(`coverage/render-gates.toml`), и сравнивать с ним в этом состоянии бессмысленно.
Замер «страницы совпадают» сделан через число страниц и `MediaBox`; попиксельное
сравнение — следующий шаг фазы вместе с растеризатором (`hayro` под фичей `raster`).

## 5. Фаза 8C — `strict-ooxml-pdf`: чтение PDF

Самая объёмная фаза. `lopdf` даёт объектную модель; **всё остальное пишем
сами** — в духе ADR-0001/0002 (свой ZIP, свой XML-слой).

| # | Требование |
|---|---|
| C1 | Страницы: дерево страниц, наследуемые `Resources`/`MediaBox`/`CropBox`/`Rotate` |
| C2 | Контент-потоки: токенизация, разбор потоков с `FlateDecode`/`LZWDecode`/`ASCIIHex`/`ASCII85`/`RunLength` (остальное — потеря в отчёте) |
| C3 | Текст: `BT`/`ET`, `Tf`, `Td`/`TD`/`Tm`/`T*`, `Tj`/`TJ`/`'`/`"`, `Tc`/`Tw`/`Tz`/`TL`/`Ts`, `cm`, `q`/`Q` → глифы с позицией, шириной, кеглем, цветом, режимом отрисовки |
| C4 | Кодировки: `/Encoding` (base + `/Differences`), `StandardEncoding`, `WinAnsiEncoding`, `MacRomanEncoding`, **`ToUnicode` CMap** (`bfchar`/`bfrange`), `Type0`/`Identity-H`/`CIDFontType2`, ширины `/Widths`, `/W` |
| C5 | Изображения: `XObject` `/Image`; `DCTDecode` → JPEG байты прозрачно; `FlateDecode` (`DeviceRGB`/`DeviceGray`) → PNG без потерь; `SMask` → альфа; `JPXDecode`/`CCITTFax`/`JBIG2` → потеря в отчёте + плейсхолдер |
| C6 | Вектор: пути (`m l c v y re h`), заливки/обводки, CTM, `cm`; кривые Безье **флэтятся** в полилинии с документированной точностью |
| C7 | Страница без текстового слоя → `ImageOnly` (вход для 8D) |
| C8 | Шифрование: не поддерживаем (RC4/AES) — `Err`, без паники |
| C9 | Лимиты: страницы, потоки, глифы на страницу, изображение, суммарный разбор |

### 5.1 Режимы результата

Один и тот же разобранный PDF даёт два разных документа:

| Режим | Что делает | Кому полезно |
|---|---|---|
| `--mode semantic` | кластеризация глифов в строки → абзацы, runs по (шрифт, кегль, цвет, начертание), заголовки по кеглю, таблицы по линейкам и выравниванию, списки по маркерам → **редактируемый `.docx`** | правка, извлечение данных |
| `--mode visual` | геометрия страницы → `sectPr`, каждый блок позиционирован якорем, кегли и интервалы подогнаны под координаты PDF → **вёрстка совпадает** | реконструкция, печать |

Оба режима — один и тот же `strict-ooxml-write` на выходе; различается только
построитель DOM. Потери фиксируются в Loss Report в обоих.

## 6. Фаза 8D — `strict-ooxml-ocr`: скан-фолбэк и графика

Требование заказчика — локальная модель через **ollama**.

**Честное ограничение, фиксируемое в заказе:** VLM — плохой текстовый OCR
(ошибки в символах, нестабильность между запусками). Поэтому текст берётся из
текстового слоя PDF, а ollama используется там, где она действительно полезна:

| Роль | Триггер | Что делает |
|---|---|---|
| `TextRecovery` | страница без текстового слоя (`C7`) | растеризация (`hayro`) → base64 → `/api/chat` с vision-моделью → абзацы; результат помечается как **восстановленный**, а не извлечённый |
| `FigureClassifier` | графический регион (изображение/вектор с площадью > порога) | растеризация региона → «таблица / рисунок / формула / логотип / диаграмма» + alt-текст в `wp:docPr/@descr` и `@title` |

| # | Требование |
|---|---|
| O1 | Трейты `TextRecovery` / `FigureClassifier`; реализация `ollama` — **только** за недефолтной фичей `ocr-ollama` |
| O2 | Вызов `POST {base}/api/chat`, `stream:false`, base64-картинка; base URL из `OLLAMA_HOST`/конфига, значение по умолчанию `http://127.0.0.1:11434` |
| O3 | Никогда не молча: каждая восстановленная страница/подпись помечается в Loss Report как `Recovered` с именем модели и версией |
| O4 | Детерминизм: при отключённой фиче вывод побайтово воспроизводим; при включённой — воспроизводимость не гейтится, но в отчёт пишется `model`, `digest`, `temperature` |
| O5 | Таймауты и лимиты ответа; ошибка ollama → `Err`, документ продолжает собираться без OCR-записей с записью в отчёт |
| O6 | Не требует сети и не требует установленного ollama, если фича выключена |

## 7. Критерии приёмки

| # | Критерий | Чем проверяется |
|---|---|---|
| **SC-1** | **Детерминизм.** Два прогона в байт. Оба направления | побитовое сравнение; `tests/determinism.rs` |
| **SC-2** | **Нет паник.** На корпусе PDF и битых файлах — только `Err` | корпус + `proptest` + fuzz-таргет `fuzz_pdf` |
| **SC-3** | **Round-trip Strict.** `parse(write(parse(x)))` ≡ `parse(x)` на Strict-корпусе | структурное равенство DOM + независимый оракул `roxmltree` + детектор Strict/Transitional |
| **SC-4** | **Открывается внешним редактором.** WPS `12.1.0.28485` открывает наш `.docx` и наш `.pdf` без ошибок | ручной прогон, результат зафиксирован в приёмке |
| **SC-5** | **PDF→Strict: текст без потерь.** Совпадение символов ≥ 99.9 % между текстовым слоем PDF и текстом `.docx` | независимое извлечение текста из нашего `.pdf` через `lopdf` |
| **SC-6** | **Strict→PDF: вёрстка не поехала.** Число страниц совпадает с SVG-рендерером; SSIM ≥ 0.95 против эталонов WPS | **тот же харнесс** `render-svg/tests/ssim.rs` + `coverage/render-gates.toml` |
| **SC-7** | **Текст в PDF живой.** `pdftotext`-эквивалент (наш же ридер на `lopdf`) возвращает читаемый текст, а не мусор; шрифты встроены | проверка наличия `FontFile2` у каждого использованного шрифта |
| **SC-8** | **Изображения.** JPEG проходит байт-в-байт; PNG — без потерь (`SSIM = 1.0` после ре-декодирования) | попиксельное сравнение |
| **SC-9** | **Вектор.** Пути PDF восстанавливаются в DrawingML `a:custGeom`; отклонение контура ≤ 0.5 pt от исходного | сравнение контуров после растеризации обоих в SVG/PNG |
| **SC-10** | **Ничего не теряется молча.** Инвариант `потеряно ⇒ записано в отчёт` (наследуем SC-4 этапа 6) | тест-инвариант над корпусом |
| **SC-11** | **OCR не в ядре.** Без фичи `ocr-ollama` вывод идентичен; с фичей — восстановленный текст помечен в отчёте | тест обеих конфигураций |
| **SC-12** | **Лицензии и лимиты.** `cargo deny check` зелёный; AGPL отсутствует | CI |

### 7.1 Цели по покрытию

| Крейт | Порог | Почему |
|---|---|---|
| `strict-ooxml-write` | ≥ 80 % строк | как у остальных |
| `strict-ooxml-render-pdf` | ≥ 80 % строк | как `render-svg` |
| `strict-ooxml-pdf` | ≥ 70 % строк (осознанно ниже) | векторная графика и шрифтовые кодировки дают много веток «крайних случаев»; 100 % недостижимо без живого корпуса PDF, компромисс фиксируется в приёмке |
| `strict-ooxml-ocr` | ≥ 60 % строк | сетевой код, проверяется мок-сервером |

## 8. Корпус

PDF-корпуса в проекте нет вообще — это отдельный пробел:

| Источник | Лицензия | Решение |
|---|---|---|
| `pdf.js` test suite, `PDFBox` test suite | Apache-2.0 / BSD | набрать 10–20 файлов в `strict-ooxml-pdf/tests/pdf/` (эталонные векторы для экстрактора) |
| `hayro` regression suite (>1000 файлов) | разнородная | **не коммитить**, использовать локально как скрипт |
| Собственная генерация | — | `xtool gen-pdf` — синтетические PDF со всеми вариантами кодировок/шрифтов; **коммитятся** (детерминированный источник регрессий) |
| WPS-эталоны | — | `kwpsconvert word2photo` → PNG, как в S4F |

Отдельный подкорпус: PDF **без** текстового слоя (скан) — для 8D, и PDF с
`Identity-H`/подмножествами шрифтов — главный источник ошибок экстрактора.

## 9. Что НЕ входит

- Зашифрованные PDF и DRM.
- Формы (AcroForm), аннотации, вложения, встроенные файлы — фиксируются как потери.
- Шрифты, встроенные в PDF без `ToUnicode`: текст восстанавливается по
  кодировке, при неоднозначности — потеря в отчёте, а не догадка.
- Кривые Безье как настоящие кривые DrawingML (только флэт в полилинии, SC-9).
- Полная типографика PDF (letter-spacing tracking, шрифтовые эффекты OpenType,
  текст по кривой) — фиксируется как потеря; в отчёте — `Partial`.
- Растровые эффекты: blur, тени, смешивание, `/Pattern` шейдинги — потеря.
- Редактирование: правки в готовом `.docx` (dif-патчи) — по-прежнему вне scope.
- Совместная работа, WASM-сборка.

## 10. Порядок работ

1. **8A.** `core::opc::zip::write` (перенос из `xtool`) → крейт `strict-ooxml-write`
   (`document.xml`, rels, content-types, media) → SC-3 → CLI `write`.
2. **8B.** Открыть `layout` в `render-svg` → крейт `strict-ooxml-render-pdf`
   (`Item` → content stream, сабсеттинг) → SC-1, SC-6, SC-7 → CLI `to-pdf`.
3. **8C.** Крейт `strict-ooxml-pdf`: страницы и лимиты → C2/C3/C4 (текст) →
   C5 (изображения) → C6 (вектор) → генератор `xtool gen-pdf` → SC-5, SC-8, SC-9.
4. **8C+.** Конвертер `pdf → wml::Document` в двух режимах + Loss Report → SC-5,
   SC-10 → CLI `from-pdf`.
5. **8D.** Трейты + `ollama` за фичей + `hayro` за фичей `raster` → SC-11.
6. ADR-0007/0008/0009, отчёт `docs/stage-8-report.md`, README, `ci.yml`,
   `deny.toml`, приёмочный документ.
