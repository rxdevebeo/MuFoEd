## 1. Блокеры

### D-1. `w:tabs` / `w:tab`: перепутаны атрибуты позиции и выравнивания

**Факт (код).** `strict-ooxml-wml/src/parse/props.rs`, `parse_tabs`
(стр. ~370–396):
- позиция берётся из `w:val` (`wml_attr(&attrs, "val")`), затем парсится как число;
- выравнивание берётся из `w:jc` (`wml_attr(&attrs, "jc")`).

**Схема.** `CT_TabStop` (WML Strict):
- `w:val` — выравнивание (`ST_TabJc`: `start/center/end/decimal/bar/num/clear`);
- `w:pos` — позиция (`ST_SignedTwipsMeasure`, twips);
- `w:leader` — заполнитель.
То есть **позиция — это `w:pos`, выравнивание — `w:val`**; атрибута `w:jc` у
`w:tab` не существует.

**Факт (реальный корпус, Word).**
```
DOCX_73_Pages_Extra_Large…docx: <w:tabs><w:tab w:val="right" w:leader="none" w:pos="9360"/></w:tabs>
styles.xml: <w:tab w:val="center" w:pos="4680"/>  <w:tab w:val="num" w:pos="720"/>  …
```

**Последствия.** Для любого реального документа: `w:val="right|left|center|num"`
не парсится как число → позиция `None`; `w:jc` отсутствует → выравнивание
всегда `Start`. **Все пользовательские табуляции теряются/искажаются.**

**Почему тесты не поймали.** Фикстура воспроизводит ту же ошибку:
`strict-ooxml-wml/tests/props.rs:39`:
```
<w:tabs><w:tab w:val="720" w:jc="center" w:leader="dot"/></w:tabs>
```
Фикстура и код согласованы между собой и оба расходятся со схемой → «зелёно».

**Требование D-1.** Читать позицию из `w:pos`, выравнивание из `w:val`
(`ST_TabJc`), заполнитель — из `w:leader`. Проверять оба атрибута на реальном
наборе значений (`left/right/center/start/end/num/bar/decimal/clear`).

**Критерии приёмки D-1.**
1. Разбор `<w:tab w:val="right" w:leader="none" w:pos="9360"/>` даёт
   `position = 9360 twips`, `alignment = End/Right`, `leader = None`.
2. Ни один `w:tab` из реальных документов корпуса не теряется (проверка на
   `tests/samples/` — см. P-1: атрибутная совместимость, а не отклонение
   Transitional).
3. Фикстура исправлена на схемную (`w:pos`/`w:val`) и добавлен кейс
   `w:val="clear"`, `w:val="num"`.
4. Golden/props-тесты обновлены и зелёные.

### D-2. Целочисленный разбор измерений: реальные документы содержат дробные значения

**Факт (код).** `strict-ooxml-wml/src/parse/mod.rs:428-440` — `parse_i32`,
`parse_u32`, `parse_u16` вызывают `str::parse::<i32/u32/u16>()`. Они
используются для измерений: `parse_width` (`props.rs:564`), `w:tblInd`
(`props.rs:440`), `w:pgMar` (`props.rs:662-668`), `w:gridCol/@w:w`
(`table.rs:66`), `w:tblW/w:tcW/wBefore/wAfter`.

**Схема.** Ширины таблиц/отступов — `CT_TblWidth`/`ST_MeasurementOrPercent`
допускают **десятичные** значения; реальный Word и вовсе пишет дробные строки.

**Факт (реальный корпус).**
```
<w:tblInd w:w="-180.0" w:type="dxa"/>          <w:tblInd w:w="17.99999999999983" w:type="dxa"/>
<w:pgMar … w:left="1872.0000000000002" w:right="1872.0000000000002" … />
```

**Последствия.** `parse_i32("-180.0")` → `None`; `parse_i32("1872.0000000000002")`
→ `None`. Значения **молча теряются** (становятся `None`), без записи в
`SupportModel`. Это тихая потеря данных на валидной (для `ST_MeasurementOrPercent`)
разметке.

**Почему тесты не поймали.** Фикстуры используют только целые
(`w:val="720"`, `w:w="2500"`, `w:left="1440"`). Дробные значения не встречаются.

**Требование D-2.** Разбирать измеряемые величины согласно их схемному типу:
- где допускается `ST_MeasurementOrPercent` (ширины таблиц/ячеек, `w:tblInd`,
  `w:wBefore/After`, `w:gridCol`) — принимать десятичные лексемы и проценты;
  приводить к модельному типу (округление/усечение) либо расширять тип;
- целочисленные измерения (`ST_SignedTwipsMeasure` и пр.) — отклонять
  нечисловые значения с фиксацией, но **не терять молча**;
- любое отброшенное значение фиксировать в `SupportModel` (как это сделано для
  enum через `record_enum`).
**Примечание к решению:** тип хранения (i32 twips vs дробный) — за разработчиком;
критерий — отсутствие тихой потери.

**Критерии приёмки D-2.**
1. `w:tblInd w:w="-180.0"`, `w:tblW w:w="1872.0000000000002"`,
   `w:pgMar w:left="1872.0000000000002"` дают числовое значение (округлённое к
   модели) либо явную запись о потере — но не тихий `None`.
2. Добавлены тесты с дробными лексическими формами (в т.ч. отрицательными).
3. Проверка на реальных документах корпуса: нет «пропавших» числовых атрибутов
   без записи в `SupportModel` (см. P-1).

## 2. Процессное требование

### P-1. Независимый оракул вместо самописных фикстур

**Проблема.** Оба блокера и три ранее самонайденных дефекта — одного класса:
**рассогласование имён/типов со схемой, скрытое согласованными фикстурами.**
Приёмка не должна зависеть от того, что автор теста и автор кода одинаково
ошибаются.

**Требование P-1 (одно или несколько):**
- **(a) Schema conformance-тест:** для каждого элемента, из которого парсер
  читает атрибуты, задан ожидаемый набор имён (выведенный из схемы Strict в
  `coverage/`), и тест проверяет, что парсер читает именно их. Ошибки вида
  `w:tab`/`w:tblInd` выявляются автоматически.
- **(b) Corpus differential:** прогон по реальному корпусу с отчётом
  «какие атрибуты/значения встретились, но не были прочитаны/распознаны»;
  расхождение — красный тест.
- **(c) Парсинг Strict-эталонов:** минимум N (≥3) реальных Strict-документов
  (не Transitional) с проверкой конкретных распознанных значений (табуляции,
  ширины, отступы). Сейчас корпус `tests/samples/` — Transitional и Stage-2
  парсер его отклоняет, поэтому реальные Strict-значения не проверяются.

**Критерии приёмки P-1.**
1. Добавлен хотя бы один из механизмов (a)/(b)/(c); он воспроизводимо
   обнаружил бы D-1 и D-2 (продемонстрировать на исправленном состоянии).
2. Отчёт/тест не «самоописываемый»: эталон имён/значений имеет внешний
   источник (схема или реальные документы).
3. Зафиксировано, как этот механизм запускается в CI.

### P-1*. Выполнено для Этапа 1 (core)

Независимый оракул для `strict-ooxml-core` **реализован**:
`strict-ooxml-core/tests/corpus_oracle.rs` (+ dev-dependency `zip` как
независимая ZIP-реализация). Тест по каждому документу публичного корпуса
`tests/samples/` проверяет без опоры на код ядра:

1. множество частей = записи архива (независимый листинг `zip`);
2. **байтовое равенство** распакованных частей независимому читателю;
3. число relationships = независимый подсчёт `<Relationship ` в сырых `.rels`;
4. каждый `<Override>` из `[Content_Types].xml` соблюдён.

Запускается в CI автоматически (входит в `cargo test --workspace --all-features`).

**Валидация оракула (важно).** При внедрении сам оракул сначала дал ложный красный
результат — две ошибки в **самом оракуле** (`"<Relationship"` совпадал с корнем
`<Relationships>`; `Path::extension()` не распознаёт dotfile `.rels`). Обе
исправлены; на данных корпуса расхождений с независимой реализацией нет. Это
подтверждает тезис P-1: оракул тоже нужно проверять.

**Остаётся открытым (Этап 2, WML):** оракул уровня атрибутов/типов (schema
conformance или corpus-differential по WML-значениям, а также парсинг реальных
**Strict**-документов) — он и выявил бы D-1/D-2. Требование P-1 для WML в силе.
